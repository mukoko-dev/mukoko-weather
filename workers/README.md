# Mukoko Weather backend (Rust Workers)

The weather backend, moving out of the Next.js app into Cloudflare Workers written in Rust ([workers-rs](https://github.com/cloudflare/workers-rs)). The plan, the inventory and the migration order are in [#148](https://github.com/mukoko-dev/mukoko-weather/issues/148).

There is **one backend for everything weather**: the Mukoko Weather app, the public weather API, the weather stations, and other apps (through the Nyuchi API for internal callers, and mukoko-api for consumers). It is split into **several Workers, one job each**, connected by service bindings, with the shared logic in one Cargo workspace.

```text
workers/
  crates/weather-core/   pure Rust, tested natively: provider normalisation, the forecast
                         contract, places, station QC and ingest keys, circuit breaker
  crates/weather-edge/   Worker helpers: JSON errors, bearer auth, timeouts
  crates/weather-mongo/  a minimal read-only MongoDB client (OP_MSG over a TLS socket, SCRAM-SHA-256, BSON)
  crates/weather-webpush/ the Web Push protocol (RFC 8291 encryption, RFC 8292 VAPID, RFC 8030 request); pure: the key
                         agreement, the ES256 signer, the transport, the clock and the salt are injected
  forecast/              mukoko-weather-forecast   provider aggregation (service binding only)
  internal-api/          mukoko-weather-internal   GET /internal/forecast for the Nyuchi API; POST /internal/ai/chat/completions
                                                   for the app's Python backend
  stations/              mukoko-weather-stations   station registration and ingest (Wunderground, Ecowitt, manual)
  places/                mukoko-weather-places     locations, search, nearest place, history, device profiles (service binding only)
  mongo-bridge/          mukoko-weather-mongo-bridge  TypeScript: device profiles and community reports in MongoDB (service binding only)
  public-api/            mukoko-weather-api        /v1/weather, /v1/forecast, /v1/air-quality (+/grid), /v1/haze, /v1/normals (+/monthly), /v1/enso, /v1/sg-air, /v1/metar,
                                                   /v1/airports/nearest, /v1/aviation/nearest-metar, /v1/model-grid, /v1/agriculture, /v1/locations, /v1/search, /v1/geo, /v1/history
  aviation/              mukoko-weather-aviation   METAR/TAF and nearest airports (service binding only)
  jobs/                  mukoko-weather-jobs       Cron Triggers: cache warming, retention, daily history
  ai/                    mukoko-weather-ai         Shamwari Weather: summaries, chat, follow-ups, history analysis
  tiles/                 mukoko-weather-tiles      weather map overlay tiles (Tomorrow.io proxy, edge + KV cache)
  d1/migrations/         schema of the D1 database `mukoko-weather` (stations, rate events, history; no device or report data)

                         and src/lib/icao-codes.ts)
```

**External station feeds** (`weather_core::external_feeds`, #361): a transformation layer, not a provider adapter. Two public networks, the Zimbabwe MSD WIS2 node (`wis2_observations`: grouped by `reportId`) and the SAAOPA WX-CoPilot API (`saaopa_aws_registry`, `saaopa_status_observations`: time is now minus age), come out as `Quantity` values: CF standard names, one UCUM unit each (m/s, hPa, Cel, mm), knots converted on the way in, station pressure and QNH kept as different quantities, and the feed's own names and units never stored. `legacy_metrics()` maps to the older km/h station names at the storage boundary only, until the weather model (`data-infra#90`) lands. No network, no clock in the parsers. `weather_core::external_fetch` is the fetch layer around them, still pure: a `Transport` trait (one GET under the request's timeout, `max_bytes` while reading and no redirects followed; a Worker implements it over `fetch`, tests over recorded fixtures), the request builders (polite `User-Agent` naming `hi@mukoko.com`, no credentials), `FeedSwitches` (every feed **off by default**; a switched-off feed makes no request), `FeedPolicy` with `due` and `backoff_ms` (never faster than the feed, doubling back-off after failures), `FetchError` (only transport errors, timeouts, 5xx, 429 and a body that is not the documented shape count against `breaker::EXTERNAL_FEED`; a 4xx never does; errors carry a stable code and no upstream text) and `Fetcher::{wis2, saaopa_status, saaopa_registry}` (WIS2 pages one window by the rows already received and the server's own `numberMatched` / `next` link, so a server that caps `limit` is still read in full, and groups the pages as one collection, once per feature, so a station-hour cut by a page boundary inside the window is repaired; a short page with no count and no link is confirmed by reading one more; `complete: false` tells the writer the window may hold more, and `Fetched::stop` / `Fetched::unwell()` tell the schedule to back off and why (a later page failed or was refused, the server ignored `offset`, or `max_pages` ran out, which is reported and never passes as a clean run); rows outside the window or stamped in the future are dropped; SAAOPA only reads stations from the reviewed registry and makes no request when none is registered). The WIS2 query parameters (`f`, `datetime`, `limit`, `offset`) follow OGC API - Features and pygeoapi conventions and are **not yet verified against the live node**; correctness does not depend on the server honouring them. No Worker calls any of this yet: the cron, the writes and the registry import wait on the gates in #361 (SAAOPA permission, target store).

**Station readings confirm frost alerts** (`weather_core::station_alert`, #361 and #289): pure rules, no Worker calls them yet. The forecast is the only thing that raises a frost alert (`push::evaluate_frost`); a registered station near the place can only add evidence to one that exists. `join_frost` takes an `Option<FrostAlert>` and answers `None` for `None`, whatever a station reads, and hands the alert back untouched (no escalation, no downgrade, no suppression: a severe alert skips quiet hours, which stays the forecast's call). The frost line and the frost window are `push::FROST_THRESHOLD_C` and `push::in_frost_window`, the ones the forecast uses, and a test sweeps both so a forecast hour and a reading can never disagree about what frost is. `readings_from_feed` joins `FeedObservation`s to the reviewed registry (`StationSite`, matched on source and `station_ref`; the position is the registry's, a station is never created from a feed) and keeps only `air_temperature` in `Cel`; rainfall is not read, so the open MSD rainfall question does not touch it. A reading is evidence only if it is finite and in range, within 25 km (and 250 m of height when both are known), at most 60 minutes old and not ahead of the clock by more than 5 minutes; each station speaks once with its latest reading, and the **nearest** usable station speaks for the place (a colder one farther away does not override it). The answer is `Confirmed` (that reading shows frost in the alert's own night), `NotYet` (usable, but warm, outside the window or from another night) or `Unconfirmed`. Only `Confirmed` has an effect: `frost_payload_with_evidence` appends one factual sentence ("A nearby station read 1°C at 23:40.", local time, no operator named, no delivery promise) and the `Evidence` goes to the delivery log. The alert is never held back waiting for a confirmation, because dedupe sends one alert per night. The limits are ours (no standard names a representative radius for a frost reading) and deliberately tight; fit them against the recorded forecast verification once it exists. Fixtures only, no network, no clock (the caller passes `now` and the place's `utc_offset_seconds`).

**Reference data** (`mukoko-weather-api`, no binding): `GET /v1/activities` (`id`, `category`, `q`, `labels`, `mode=categories`), `/v1/suitability` (`key`), `/v1/tags` (`featured=true`), `/v1/regions`, `/v1/ai/prompts` (`key`) and `/v1/ai/suggested-rules`, with the shapes and ordering of the old `/api/py/*` routes (`weather_core::reference`). The Python backend read these from MongoDB, where `/api/db-init` had copied the app's seed files; the Workers hold no database connection (#150), so the same documents are compiled in from `crates/weather-core/data/reference/*.json`, generated by `scripts/gen-reference-data.mjs` (CI fails when they are stale). To change one, edit the seed file in `src/lib/`, run the generator, then `prettier --write` on the JSON. Differences from Python: text search is an OR of stemmed terms over label, description and category (the MongoDB text index's behaviour, not its scoring); the data-managed `aiInstructions` on an activity lived only in MongoDB and is not served; the `system:*` prompts are never served (the AI Worker has them compiled in).

**`mukoko-weather-places`** (service binding only, from `mukoko-weather-api` as `PLACES`) also serves the device preference profiles (`POST /v1/devices`, `GET` and `PATCH /v1/devices/{id}`, ported from `api/py/_devices.py`): one document per device in MongoDB (`device.device_profiles`), last write wins, written and read by `mukoko-weather-mongo-bridge` through the `MONGO_BRIDGE` service binding (never D1; **deploy the bridge before this Worker**), 20 new profiles an hour per client (D1 `rate_events`). It serves `/v1/locations`, `/v1/search`, `/v1/geo` and `/v1/history` with the parameters and shapes of `/api/py/locations|search|geo|history`. It reads no database for places: the seed locations (with their tags) are compiled in; a `{name}--{geohash}` slug carries its own point (the app's smart slugs, which `mukoko-weather-forecast` now resolves too); canonical places come from the Nyuchi API (`/v1/places`, `/v1/places/nearby`, `/v1/places/{slug}`); geocoding comes from Open-Meteo (forward) and Nominatim (reverse, rate limited per client), all cached in KV. `geo?autoCreate=true` names the point and answers its `{name}--{geohash}` slug, but writes no canonical place. `search` tops a thin answer up from the geocoder and offers a country, province or continent itself as the LAST results (a spot at its centre, `area` set; a slot is reserved for it), after the places and the best cities of a country the query named, deduped against the seed list (`phuket-th`). `geo` never dead-ends: a seed within 150 km, else a spot named by a cached, budgeted city-level Nominatim lookup of the ~1 km cell, else a coordinate label spot (`12.35°N 45.62°E`). `named: false` means a definitive nothing here; `namingSkipped: true` (over budget, an outage, or `noName=1` from a server caller) says nothing about the point, is `no-store`, and `autoCreate=true` returns a seed within 50 km instead of a label when naming was skipped. Nominatim has its own hourly D1 budget (60/h per client, 3,000/h service-wide) besides the per-minute `GEOCODE_LIMITER`. Nothing is stored. `search?q=<name>&mode=resolve` is the one best place for a bare name in a URL (`/koh-samui`): the app's proxy 308-redirects to its `{name}--{geohash}` slug (`weather_core::resolve`; it stores nothing, and answers `resolve` = `ok` | `no_match` | `over_budget` | `unavailable`). Uncached forward geocodes spend an hourly budget kept in D1 `rate_events` (`weather_core::budget`; per client and service-wide; resolve and search are separate budgets, resolve 60/h per client and 150/h service-wide, search 120 and 350, so autocomplete cannot starve a bare-name resolve; it fails closed). The client key is a hash of a verified token subject when a verifier exists (none yet: the issuer is a platform responsibility, #148), else of the IP. Answers are cached in KV (hits a day, misses ten minutes; "nothing here" is stored as a `Slot`, never a bare `null`, which KV reads back as a miss); a budget, over-budget or outage answer is `no-store`. **`/v1/history`** (`GET ?location=` and/or `lat=&lon=`, `days=` 1..3660 or `start=&end=`; `src/history.rs`, rules in `weather_core::history`) reads our own store first and pulls ONLY the missing past dates from an external archive: the days `mukoko-weather-jobs` RECORDED (D1 `place_daily`, seed places), then MongoDB `weather.weather_history` through the bridge (the days the Python backend recorded until 2026-10-18 and every archive day), then NASA POWER and Open-Meteo's ERA5 archive (order `HISTORY_PROVIDERS`, default `nasa-power,open-meteo-archive`) for the rest: newest runs first, chunked to each provider's span, at most 6 upstream calls and 20 s a request, the fetched days written back through the bridge insert-only (`POST /history/days`) after the answer is sent (`wait_until`). Any coordinate on Earth works (a spot is stored under `geo:<geohash7>`, a bare coordinate under its 0.05° `cell:` key; both limited to the newest 366 days). Never fails the answer for a provider (it falls to the next, then to what is held; a bridge that is down means the fetched days are returned and not stored); a day carries `source` `recorded` | `nasa-power` | `open-meteo-archive` and the answer carries `sources` (attribution), `backfilled`, `missing`, `clamped`. D1 `rate_events` budgets: `history-backfill` 30/h per client (`history-backfill-coords` 10/h for a spot or bare coordinate; spent only when a call goes upstream), `history-nasa-power` 600 calls/h, and `history-open-meteo` in WEIGHTED units (a year of 19 variables is about 50 of Open-Meteo's own billing units; 250/h service-wide, 150/h per client, at most 150 units per request). When D1 or the bridge cannot be read nothing is fetched and the answer is `no-store` (`degraded: true`; so is any answer cut short by a spent budget, an open breaker, a provider failure or a cap while dates are still missing, and only a plain archive lag is cached, 60 s); it is a 502 only when no store was actually read; the fetched days are stored in the background (`saving: true`; a failed save logs the HTTP status and the bridge's error code). A place's days recorded under its platform slug (`nairobi-518dd4`) are merged in too: the bridge finds that slug in `places.placesGeo` (read-only) near the place's own point. A budget spend is one guarded D1 statement (the rows are inserted only if both hours have room, and the change count is the decision), so parallel requests cannot all pass. Provider chunks are cached 3 h in KV (`hist:v1:`). Optional config: vars `HISTORY_PROVIDERS`, `HISTORY_COMMERCIAL_ONLY` (`1` drops Open-Meteo unless a key is set: its free host is non-commercial) and the optional plain secret `OPEN_METEO_API_KEY` (a paid plan; switches to the commercial archive host; deliberately not a Secrets Store binding, because a binding to a store secret that does not exist fails the deploy). Bindings: KV `CACHE` (the forecast namespace), D1 `WEATHER_DB` (reads `place_daily`, writes `rate_events`), service `MONGO_BRIDGE`, rate limit `GEOCODE_LIMITER`, secret `NYUCHI_API_KEY`, var `NYUCHI_API_URL`.

**Developer keys.** `mukoko-weather-api` stays open to anonymous callers (120 a minute per IP). A developer may send a Nyuchi API key (`X-API-Key: nyk_….nys_…`, or `X-Client-Id` and `X-Client-Secret`) scoped for `weather`. The Worker keeps no key store: it forwards the key to the Nyuchi API's `GET /v1/weather/key`, which validates it, enforces the monthly quota and counts the call, and keeps a good answer in memory for 60 seconds (under a SHA-256 of the key), so usage is counted per check, not per request. A keyed caller is limited per key (`KEY_RATE_LIMITER`, 600 a minute). A bad key is `401`, a key without `weather` is `403`, and if the Nyuchi API cannot answer the call is refused with `503` (fail closed). Keys are created in the Nyuchi API (`POST /v1/api-keys`).

**Place knowledge** (`GET /v1/locations/profile?slug|lat&lon[&country]`: `mukoko-weather-forecast` `/profile`, relayed by `mukoko-weather-api`; `weather-core` `place_profile`, `climate_normals` and `ag_calendar`; ported from the Python route and pinned to it by `tests/fixtures/place-profile.json`) returns what we know about a place that changes slowly, with its source and licence per field, and `current` computed at read time. Nothing is stored. Three things differ from the Python, so read them before relying on the route:

- **No MongoDB.** The forecast Worker has no Mongo binding (no `MUKOKO_WEATHER_MONGODB_URI` in its `secrets_store_secrets`, and no plain `MONGODB_URI` secret unless the owner set one), so the Mongo season rows (`weather.seasons`, including the AI-made ones) and a stored neighbour's `placeKnowledge` are never read; both paths fall back and stay dead until the owner step in "MongoDB from a Worker" is done. A country missing from the compiled `crates/weather-core/data/seasons.json` gets a derived hemisphere or wet/dry calendar where the Python served the stored rows.
- **`place_near` knows only the seed places.** The nearest-place lookup searches the compiled-in seed places within 3 km (`NEAREST_PLACE_KM`), not `placesGeo`. A bare coordinate near an African town that is not a seed gets no country, so no GEOGLAM crop calendar and no season calendar, unless the caller passes `country` (the location page does). A place the Nyuchi API resolves has no province (`admin1`).
- **New KV keys, and the archive is fetched three times.** Soil and normals are cached under `soil:v1:` and `nrm:v1:`. The same 30-year ERA5 archive request is made separately by `/normals`, `/monthly-normals` and `/profile` for a cold 0.25° cell (up to three requests where the Python made one). All three sit behind the Open-Meteo breaker; only `/profile` is metered: 120 builds an hour per client and 600 service-wide (`Action::PlaceProfile`, D1 `rate_events`, no migration needed). The unit is taken only when an upstream call will really go out, so a request answered from KV, or one whose Open-Meteo or SoilGrids breaker is open, costs none.

**Deploy order against Vercel.** When a route is ported, its Python route is deleted in the same PR and the app calls `weather-api.mukoko.com` with **no `/api/py` fallback** (`src/lib/weather-api.ts`). The Workers deploy by hand and the Vercel release is promoted separately, so a Vercel release promoted before the Workers carries a call to a route that does not exist yet: it answers `404` and the card it feeds (for the profile route, the place-knowledge rows of the About card) renders nothing until the Workers are up. Deploy `forecast` first, then `public-api` (the order `all` uses; nothing else needs deploying for a route that adds no binding, secret or migration), check `/health` and the new route, and only then promote Vercel. Rolling the Workers back past a ported route breaks the live app the same way, so roll Vercel back first.

## Shamwari Weather (the AI Worker)

```text
POST /internal/summary        {location: {slug, name, lat, lon, elevation, country, tags}, activities}
                              → {insight, cached, generatedAt}
                              (only from mukoko-weather-internal, for the signed-in app; not public)
POST /v1/ai/followup          {message, locationName, locationSlug, weatherSummary, activities, season, history}
                              → {response}
POST /v1/ai/chat              {message, history, activities} → {response, references: [{slug, name, type}]}
POST /v1/ai/history/analyze   {location, days: 7..365, activities} → {analysis, stats, cached, dataPoints}
```

- **Guardrails.** `GET {NYUCHI_API_URL}/v1/ai/guardrails/compiled?applies_to=weather` with `X-API-Key`. The block is used for 60 seconds, then revalidated with `If-None-Match`. If the API can't be reached, the last block is used for up to 24 hours. With no usable block every route answers `503 guardrails_unavailable`.
- **Model calls.** `env.AI.run(model, input, {gateway: {id: "shamwari", collectLog: false, metadata}})`. The metadata names the route only, never user content. A Guardrails or DLP block (2016, 2017, 2029, 2030) is answered with a polite refusal; a gateway rate limit with `429`.
- **The summary** is a signed-in route of the app, not a public one (`weather_core::ai::summary` and `prompts`, pinned to the Python it replaced by `tests/fixtures/ai-summary.json`). The app's `/api/ai` proxy checks the WorkOS session, then calls `mukoko-weather-internal` `POST /internal/ai/summary` with the service key, `X-Mukoko-User-Id` and `X-Mukoko-Client-IP`; that Worker forwards to this one's `/internal/summary`. These paths have no public route and `mukoko-weather-api` forwards `/v1/ai/*` only, so the sign-in gate cannot be bypassed. The Worker fetches the weather itself from `forecast`; the `weatherData` a client sends is ignored. The prompt is byte for byte the Python's: the location, its tags, the user's activities (known ids only, at most three, with their labels and the per-activity guidance from `data/reference/activity-guidance.json`), the season (the country's calendar from the compiled seed, else the hemisphere's) and the place profile block (`forecast` `GET /profile/prompt`, cache-only, 4 s bound). The entry is cached in KV for 30 minutes for a `city`, 60 for a farming, mining, education or border place and 120 otherwise, under the place and the sorted activities (a seed city by its slug; anywhere else by the ~1 km cell and a hash of what the client said, so no caller reads another's text), and redone early when the temperature moves more than 5 degrees or the weather code changes. If the model fails, the plain-conditions text is served and cached for a minute. Only a call that goes to the model is counted: 30 an hour per person and 1,500 an hour for the service (D1 `rate_events`, action `ai-summary`, fails closed), answered `429` with `Retry-After` beyond that.
- **The chat** has no tools. The seed places named in the message (or, failing that, earlier in the conversation) are looked up first, up to three, and their forecasts go into the prompt. `references` lists them.
- **History** reads the same history the app shows, from `mukoko-weather-places` over the `PLACES` binding (recorded days, stored archive days, and an archive fetch for the rest), for `days` 7..3660 or `start`/`end`. No rows gives `404 no_history`; the places Worker not answering gives `502 history_unavailable`. Analyses are cached for an hour, keyed on the data.

- **The backend passthrough.** `POST /internal/chat/completions` takes an OpenAI chat-completions body (`messages`, `tools`, `max_tokens`, optional `model`) from the Python backend, through `mukoko-weather-internal` (which checks `WEATHER_SERVICE_API_KEY`; `mukoko-weather-api` never forwards this path). It rebuilds the messages from known keys, puts the guardrails first in the one system message, refuses user turns with personal data (`422`), runs `env.AI.run` through the gateway with any `tools`, and answers an OpenAI chat completion with `content` only (never `reasoning_content`) and OpenAI-shaped `tool_calls`, so the Python tool loops are unchanged. No per-IP limit here (every backend call shares one key); the backend limits per visitor. Logic: `weather-core/src/ai/completions.rs`.
- **The model and its budget.** `AI_MODEL` is `@cf/zai-org/glm-5.3-flash` (Z.ai GLM-5.3 Flash: function calling and reasoning). Only `@cf/` ids are accepted (`allowed_model`); the default is `weather_core::ai::DEFAULT_MODEL`. For reasoning models every call adds `REASONING_HEADROOM` (1024) to `max_tokens` and sends `reasoning_effort: "low"`; GLM cannot switch reasoning off, and an answer whose budget went on reasoning comes back empty (`502 model_failed`).

Not ported from the Python backend: the chat's tool loop (search beyond the seed places, places by tag) and the AI-made season rows in MongoDB `weather.seasons` (a country the compiled seed lacks gets the hemisphere's season). The prompts are compiled in (`weather-core/src/ai/prompts.rs`); the per-activity guidance (`aiInstructions`) is a snapshot of the 55 production documents taken on 2026-11-01, so editing it in MongoDB no longer reaches the model.

## The internal forecast contract

This is the upstream for the Nyuchi API's `GET /v1/weather/forecast` (nyuchi/api-gateway#154). The Nyuchi API needs two settings:

- `WEATHER_SERVICE_URL=https://weather-internal.mukoko.com`;
- `WEATHER_SERVICE_API_KEY`, set to the same value as this Worker's secret.

```text
GET /internal/forecast?location=<slug|name>        (or lat=&lon=)   [&days=1..7, default 7]
Authorization: Bearer <WEATHER_SERVICE_API_KEY>

200 {"location": {"slug", "name", "lat", "lon"},
     "data": [{"date": "YYYY-MM-DD", "description", "weather_code", "high", "low",
               "precipitation_probability"}],
     "source": "tomorrow" | "open-meteo",
     "fetched_at": "RFC 3339",
     "attribution": "provider credit line"}
401 missing or wrong key       404 unknown location     422 bad query
503 no key configured here, or no provider answered (fails closed)
```

**How a place is resolved.** Locations resolve in this order:

1. the app's seed locations (compiled in), matched by slug, by name, or by the name's slug;
2. the Nyuchi API (`GET /v1/places/{slug}`, cached), because canonical place records belong to the API;
3. otherwise `404`.

**Requests by point.** A `lat`/`lon` request borrows the slug and name of a seed location within 10 km. Otherwise the slug is the rounded point and the name is `null`.

## Web Push alerts ([#289](https://github.com/mukoko-dev/mukoko-weather/issues/289))

Frost first, then severe weather, as Web Push to a browser that opted in. **Built:** the rules of what to send (`weather_core::push`: validation of an endpoint against an allow list, preferences, quiet hours, per-day and per-night caps, dedupe, the frost evaluation, the payload, what a push service's status means) and the protocol that carries a decided alert (`crates/weather-webpush`). **Not built:** the Worker that holds the key and does the `fetch` and the WebCrypto calls, the evaluator tick in `mukoko-weather-jobs`, and the Nyuchi API routes that store subscriptions and preferences (`/v1/notifications/*`, nyuchi/nyuchi-api); nothing in this repo can send a push yet.

`weather-webpush` is pure like `weather-core`: it holds no key, reads no clock, draws no random number, does no elliptic-curve arithmetic and opens no connection. The runtime injects each of those through three small traits and two arguments:

- `Transport`: the POST (a Worker wraps `fetch`, without following redirects).
- `Es256Signer`: the ES256 signature of the VAPID token. It owns the private key (a WebCrypto key imported from a secret binding), returns the raw 64-octet `r || s`, and reports the public key.
- `KeyAgreement`: a fresh ephemeral P-256 key pair and the ECDH shared secret with the browser's key, rejecting a point that is not on the curve.
- The current time and the 16-byte per-message salt (`crypto.getRandomValues`) are arguments.

**No Rust elliptic-curve crate is used.** RustCrypto's `p256` 0.13 resolves `crypto-bigint` 0.5, which `cargo audit` reports as RUSTSEC-2026-0387 (timing variability in operations meant to be constant-time; fixed only in 0.7.6, which that chain does not accept), and a security finding stays open until the owner decides. The intended implementation of `KeyAgreement` and `Es256Signer` is the Workers runtime's own WebCrypto (`crypto.subtle`: `generateKey` and `deriveBits` with ECDH P-256, `sign` with ECDSA P-256 SHA-256, whose output is already `r || s`), which is native code and adds no crate. That is decided as a direction, not built. What stays in the crate is everything deterministic: the HKDF-SHA-256 key derivation and the AES-128-GCM record (`hkdf`, `aes-gcm`: no advisory), the header, the JWT, the request. It builds for `wasm32-unknown-unknown` with no JS shim and tests natively on the RFCs' own vectors.

| Module    | Standard                                                                        | Pinned by                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `encrypt` | RFC 8291 message encryption over the RFC 8188 `aes128gcm` content coding        | the RFC 8291 section 5 worked example, byte for byte, from the RFC's own ECDH secret and public key (its printed `Content-Length: 145` is off by one; the body is 144 octets)           |
| `vapid`   | RFC 8292 voluntary application server identification (ES256 JWT, `vapid t=,k=`) | the RFC 8292 section 2.4 JWT signing input, byte for byte; the signer sees exactly `header.claims`; claims in the RFC's order; 12 hour expiry; the audience only ever an allowed origin |
| `request` | RFC 8030 (`TTL`, `Urgency`, the encrypted body) and the injected `Transport`    | headers, the audience being the push service origin, build errors that say whose fault they are, a full decrypt of the built request                                                    |

Safety properties the tests hold: an endpoint outside the allow list (`weather_core::push::validate_endpoint`: https, a known push service, the default port only, no credentials) is refused before anything is signed or encrypted, so the sender cannot be pointed at an internal address, and a VAPID token is only ever made for an allowed origin; `Debug` of a request, a subscription, a recipient or an agreement never prints the endpoint, a key, a token or a body (an endpoint is a bearer capability; logs carry `weather_core::push::endpoint_id`, a SHA-256); a push service's answer is classified by `weather_core::push::classify_status` (a 404, 410 or 403 deactivates the subscription, a 429, 5xx or a timeout is retried on a later tick, any other 4xx is not), and `Outcome::delivery_status` maps it onto the `platform.alertDeliveries.status` values of the data-infra model. Delivery is best effort and nothing here promises it.

For the evaluator tick (step d), two things this crate deliberately does not decide: the TTL and urgency of an alert (they belong with the alert, next to `frost_payload`: a "tonight" message must expire with its night, and severe frost is `High`), and a guard on `Expired`: a wrong or rotated VAPID key, or a clock far off, makes a push service answer 403 to every send, so a run in which every send in a batch is `Expired` is an operator problem and must deactivate nothing.

The VAPID key pair is an **owner step**: generate it once (a P-256 key; the private half is a Secrets Store secret, the public half is what the Nyuchi API serves from `GET /v1/notifications/push/config` and a browser subscribes against) and set the contact `mailto:`. Never generate or store it from code in this repo. Changing the pair later invalidates every subscription.

## MongoDB from a Worker

Workers cannot use the `mongodb` crate, and the Atlas Data API was shut down on 30 September 2025, so `crates/weather-mongo` speaks the wire protocol itself over `worker::Socket` (outbound TLS): `OP_MSG`, SCRAM-SHA-256 and a small BSON codec. The logic is tested natively (the BSON specification examples, the RFC 7677 SCRAM vector, and a scripted server that runs the whole login), but it has not yet been run against a live cluster: use the probe below as the first check.

Owner steps:

1. **Atlas network access.** A Worker has no fixed address, so the Atlas project's IP access list must allow `0.0.0.0/0` (Atlas, Network Access). Protect the cluster with a dedicated database user instead: a **read-only** user (`read` on `weather` and `places`) named for this backend, with a long generated ASCII password (SCRAM-SHA-256; a non-ASCII password is refused).
2. **The connection string, as a seed list.** A Worker cannot resolve `mongodb+srv://`. In Atlas, "Connect" then "Drivers", choose an older driver version to show the `mongodb://` form that lists every shard host, and keep `authSource=admin`:
   `mongodb://USER:PASSWORD@ac-xxxx-shard-00-00.xxxx.mongodb.net:27017,ac-xxxx-shard-00-01.xxxx.mongodb.net:27017,ac-xxxx-shard-00-02.xxxx.mongodb.net:27017/weather?replicaSet=atlas-xxxx-shard-0&authSource=admin&tls=true`
3. **The secret.** Create it in the Secrets Store as `MUKOKO_WEATHER_MONGODB_URI` (scope `workers`), then add the `secrets_store_secrets` binding to each Worker that reads MongoDB and list that Worker in `weather_core::secrets::ALL`. Until then, set the plain secret on that Worker: `npx wrangler secret put MONGODB_URI -c <worker>/wrangler.jsonc`. (Do not add the binding before the store secret exists: Cloudflare refuses the deploy, error 10182.)
4. **Check it.** `GET` the forecast Worker's `/health?probe=mongo` (through a service binding, or `wrangler dev`) answers `mongo_probe: {"ok": true}` once the network path, the string and the login all work; on failure it names the problem (never the string).

## The MongoDB bridge

Devices and community reports are stored in MongoDB, not D1. `weather-mongo` is read-only, so writes go through `mongo-bridge` (`mukoko-weather-mongo-bridge`, TypeScript): one Durable Object holds one `MongoClient` from the official `mongodb` driver (`nodejs_compat`), so the connection is set up once instead of about 300 ms per request. A `MongoClient`, `Db` or `Collection` cannot cross RPC, so all database logic runs inside the object and callers speak narrow JSON over HTTP. It has no route and no workers.dev address; only a Worker with a `MONGO_BRIDGE` service binding (`places`) can call it.

| Route (bridge)                                          | Collection                                                                                                                                   |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /devices`, `GET`/`PATCH /devices/{id}`            | `device.device_profiles` (`{deviceId, preferences, createdAt, updatedAt}`)                                                                   |
| `POST /reports`, `GET /reports`, `POST /reports/upvote` | `weather.weather_reports` (the shape `api/py/_reports.py` wrote)                                                                             |
| `GET /history`, `POST /history/days`                    | `weather.weather_history` (`{locationSlug, date, source, current, daily, insights?, recordedAt}`; read any source, INSERT archive days only) |

The document shapes are the existing ones: nothing is migrated. Every route validates its input with the rules of `weather_core::community` (the Rust Worker checks first, the bridge again), builds its own query from the validated fields (no filter, update or projection from the caller), bounds every list (at most 20), and applies an upvote in one atomic update (`$addToSet` plus `$inc`, only when the voter is new). Indexes are never created from code. The history routes are bounded the same way: a read is at most 3 keys over 3660 days; a write is at most 800 archive days (the body cap for that route is 1 MiB, the others 16 KiB) whose `source` must be `nasa-power` or `open-meteo-archive` (a `recorded` day can never be written through the bridge), whose fields are an allowlist of typed numbers and `YYYY-MM-DDTHH:MM` strings, and whose dates are past and at least 1940; the document is built by the bridge, inserted `$setOnInsert` with upsert (unordered, a duplicate-key race is not an error), so a stored day is never overwritten. Per-client limits (20 fresh devices an hour; the history budgets) stay in the calling Worker, in D1 `rate_events`.

Owner steps:

1. **Atlas user.** Create a read-write database user for the bridge (`readWrite` on `device` and `weather`, plus `read` on the collection `places.placesGeo`, which the history route reads to find a place's platform slug; nothing else), with a long generated ASCII password. Without the `places` read the bridge still works: the alias lookup fails closed (no alias days are merged, one warning with the error name, retried after 5 minutes). The Atlas IP access list already allows Workers (see "MongoDB from a Worker").
2. **The secret.** Put the seed-list connection string (the same form as in "MongoDB from a Worker", with this user, `authSource=admin`) in the Secrets Store as `MUKOKO_MONGODB_RW_URI` (scope `workers`) BEFORE the first deploy: a binding to a store secret that does not exist fails the deploy. The bridge reads the store binding, and falls back to a plain Worker secret `MONGODB_RW_URI` (`npx wrangler secret put MONGODB_RW_URI -c mongo-bridge/wrangler.jsonc`) while the store entry is missing.
3. **Indexes** (Mongo shell; not created from code): `weather.weather_reports` TTL index on `expiresAt` with `expireAfterSeconds: 0` and `{locationSlug: 1, reportedAt: -1}`; `device.device_profiles` unique `deviceId`; `weather.weather_history` already has its unique `{locationSlug: 1, date: -1}` index (db-init created it), which is what makes the history insert-only upsert race-safe. Without the unique indexes two simultaneous creates of one new device id (or of one history day) could both insert. The bridge's read-write user needs `readWrite` on `weather` already (reports).
4. **Deploy order.** `mongo-bridge` (`cd mongo-bridge && npm ci && npx wrangler deploy`), then `places`, then `ai` (it binds `places` for the history analysis), then `public-api` if it changed. Check it: `GET /health?probe=mongo` on the bridge (through the binding or `wrangler dev`) answers `mongo_probe: {"ok": true}` once the network path, the string and the login work; on failure it says `not_configured` or `unreachable`, never the string.

## Rules

- **Cloudflare only.** Work that does not fit a Worker goes to Queues, Cron Triggers, Durable Objects, Workflows or Containers, never another host.
- **MongoDB, read-only, through `weather-mongo`.** The Workers keep weather data in their own D1, KV and R2, and may read the shared MongoDB (`places`, `weather` reference data) with `weather_edge::mongo(env)`: `find`, `find_one` and `aggregate` only (no `$out` or `$merge`), read preference secondary-preferred, a server-side time limit and a cap on the documents returned. It needs the connection-string secret and the owner steps below. Canonical records are still written only through the Nyuchi API (#150).
- **Keep each Worker small.** Budget its CPU, memory, bundle size and subrequests. Split a Worker, or fan out over a Queue, rather than grow one.
- **Observability.** Traces and invocation logs are on, with query strings redacted. The code never logs payloads, coordinates or keys.
