# Mukoko Weather backend (Rust Workers)

The weather backend, moving out of the Next.js app into Cloudflare Workers written in Rust ([workers-rs](https://github.com/cloudflare/workers-rs)). The plan, the inventory and the migration order are in [#148](https://github.com/mukoko-dev/mukoko-weather/issues/148).

There is **one backend for everything weather**: the Mukoko Weather app, the public weather API, the weather stations, and other apps (through the Nyuchi API for internal callers, and mukoko-api for consumers). It is split into **several Workers, one job each**, connected by service bindings, with the shared logic in one Cargo workspace.

```text
workers/
  crates/weather-core/   pure Rust, tested natively: provider normalisation, the forecast
                         contract, places, station QC and ingest keys, circuit breaker
  crates/weather-edge/   Worker helpers: JSON errors, bearer auth, timeouts, the feed transport (dark)
  crates/weather-mongo/  a minimal read-only MongoDB client (OP_MSG over a TLS socket, SCRAM-SHA-256, BSON)
  crates/weather-webpush/ the Web Push protocol (RFC 8291 encryption, RFC 8292 VAPID, RFC 8030 request); pure: the key
                         agreement, the ES256 signer, the transport, the clock and the salt are injected
  forecast/              mukoko-weather-forecast   provider aggregation (service binding only)
  internal-api/          mukoko-weather-internal   GET /internal/forecast for the Nyuchi API; the signed-in app's /internal/ai/* routes
                                                   (and the OpenAI-style /internal/ai/chat/completions passthrough, now without a caller)
  stations/              mukoko-weather-stations   station registration and ingest (Wunderground, Ecowitt, manual)
  places/                mukoko-weather-places     locations, search, nearest place, history, device profiles (service binding only)
  mongo-bridge/          mukoko-weather-mongo-bridge  TypeScript: device profiles and community reports in MongoDB (service binding only)
  public-api/            mukoko-weather-api        /v1/weather, /v1/forecast, /v1/air-quality (+/grid), /v1/haze, /v1/normals (+/monthly), /v1/enso, /v1/sg-air, /v1/metar,
                                                   /v1/airports/nearest, /v1/aviation/nearest-metar, /v1/model-grid, /v1/agriculture, /v1/locations, /v1/search, /v1/geo, /v1/history
  aviation/              mukoko-weather-aviation   METAR/TAF and nearest airports (service binding only)
  jobs/                  mukoko-weather-jobs       Cron Triggers: cache warming, retention, daily history
  push/                  mukoko-weather-push       Web Push sender, runtime half: WebCrypto key agreement and signer, fetch transport (dark, not deployed)
  ai/                    mukoko-weather-ai         Shamwari Weather: summaries, chat, follow-ups, history analysis
  tiles/                 mukoko-weather-tiles      weather map overlay tiles (Tomorrow.io proxy, edge + KV cache)
  d1/migrations/         schema of the D1 database `mukoko-weather` (stations, rate events, history; no device or report data)
  scripts/               gen-reference-data.mjs (activities, suitability rules, tags, regions, AI prompts), and
                         gen-seed-locations.mjs (seed places, airports and the legacy to canonical
                         slug pairs, from src/lib/locations.ts, src/lib/icao-codes.ts
                         and src/lib/slug-migration-data.ts)
```

**External station feeds** (`weather_core::external_feeds`, #361): a transformation layer, not a provider adapter. Two public networks, the Zimbabwe MSD WIS2 node (`wis2_observations`: grouped by `reportId`) and the SAAOPA WX-CoPilot API (`saaopa_aws_registry`, `saaopa_status_observations`: time is now minus age), come out as `Quantity` values: CF standard names, one UCUM unit each (m/s, hPa, Cel, mm), knots converted on the way in, station pressure and QNH kept as different quantities, and the feed's own names and units never stored. `legacy_metrics()` maps to the older km/h station names at the storage boundary only, until the weather model (`data-infra#90`) lands. No network, no clock in the parsers. `weather_core::external_fetch` is the fetch layer around them, still pure: a `Transport` trait (one GET under the request's timeout, `max_bytes` while reading and no redirects followed; a Worker implements it over `fetch`, tests over recorded fixtures), the request builders (polite `User-Agent` naming `hi@mukoko.com`, no credentials), `FeedSwitches` (every feed **off by default**; a switched-off feed makes no request), `FeedPolicy` with `due` and `backoff_ms` (never faster than the feed, doubling back-off after failures), `FetchError` (only transport errors, timeouts, 5xx, 429 and a body that is not the documented shape count against `breaker::EXTERNAL_FEED`; a 4xx never does; errors carry a stable code and no upstream text) and `Fetcher::{wis2, saaopa_status, saaopa_registry}` (WIS2 pages one window by the rows already received and the server's own `numberMatched` / `next` link, so a server that caps `limit` is still read in full, and groups the pages as one collection, once per feature, so a station-hour cut by a page boundary inside the window is repaired; a short page with no count and no link is confirmed by reading one more; `complete: false` tells the writer the window may hold more, and `Fetched::stop` / `Fetched::unwell()` tell the schedule to back off and why (a later page failed or was refused, the server ignored `offset`, or `max_pages` ran out, which is reported and never passes as a clean run); rows outside the window or stamped in the future are dropped; SAAOPA only reads stations from the reviewed registry and makes no request when none is registered). The WIS2 query parameters (`f`, `datetime`, `limit`, `offset`) follow OGC API - Features and pygeoapi conventions and are **not yet verified against the live node**; correctness does not depend on the server honouring them. The Worker side of the `Transport` is `weather_edge::feed_transport::WorkerTransport` (**dark: nothing constructs it, no cron calls it and every `FeedSwitches` flag is still off**), and its rules are the pure `weather_core::external_transport`, tested natively: `redirect: "manual"`, so a 3xx comes back as a 3xx status (never followed, its body never read, `Location` never looked at, and it never counts against the breaker); the body is read from the response stream chunk by chunk and the transfer is cancelled at the request's `max_bytes` (`read_bounded`: a body that passes the limit is `TransportError::TooLarge` and **no partial body is ever returned as a success**; a declared `Content-Length` over the limit fails before the first byte is read; no `.text()`, `.bytes()` or `.json()`, which would buffer the whole body first); the request and the reading of its body run under ONE deadline, the policy's `timeout_ms` (`with_deadline`: when it passes, the in-flight request is aborted through its `AbortSignal` and the result is a timeout, while an answer that is ready in the same poll still wins); and `check_request` refuses, before anything is sent, a URL that is not `https` to one of the two feed hosts (credentials in the URL, a port or a look-alike host all fail the exact host match), a query parameter named like a secret (`key`, `token`, `secret`, `pass`, `auth`, `cred`, `sig`, `session`, `cookie`, `bearer`, `jwt`, after percent-decoding), any header but `User-Agent` and `Accept` (so no `Authorization`, `Cookie` or API-key header can go out), a missing `User-Agent`, a request that asks to follow redirects and a zero timeout or limit. A refused request is `TransportError::Refused` (`FetchError::Refused`, code `refused_request`; ours, so it does not open the breaker), a body that is not UTF-8 is `NotText` (`not_utf8`) and an over-long one is `too_large`. The Worker side logs nothing and its errors are a stable code, never a URL, a header or a byte of a body. The glue file itself needs the Workers runtime and has no native test; a source-scan test in `weather_core::external_transport` pins that it keeps to these rules (a tripwire, not a behaviour test), and the first scheduled call is the first run against a real node. **Where the readings are stored is decided later**: the transport and the fetch layer return them in memory, and nothing here chooses or builds a store. The cron, the writes and the registry import wait on the gates in #361 (SAAOPA permission, target store).

**Station readings confirm frost alerts** (`weather_core::station_alert`, #361 and #289): pure rules, no Worker calls them yet. The forecast is the only thing that raises a frost alert (`push::evaluate_frost`); a registered station near the place can only add evidence to one that exists. `join_frost` takes an `Option<FrostAlert>` and answers `None` for `None`, whatever a station reads, and hands the alert back untouched (no escalation, no downgrade, no suppression: a severe alert skips quiet hours, which stays the forecast's call). The frost line and the frost window are `push::FROST_THRESHOLD_C` and `push::in_frost_window`, the ones the forecast uses, and a test sweeps both so a forecast hour and a reading can never disagree about what frost is. `readings_from_feed` joins `FeedObservation`s to the reviewed registry (`StationSite`, matched on source and `station_ref`; the position is the registry's, a station is never created from a feed) and keeps only `air_temperature` in `Cel`; rainfall is not read, so the open MSD rainfall question does not touch it. A reading is evidence only if it is finite and in range, within 25 km (and 250 m of height when both are known), at most 60 minutes old and not ahead of the clock by more than 5 minutes; each station speaks once with its latest reading, and the **nearest** usable station speaks for the place (a colder one farther away does not override it). The answer is `Confirmed` (that reading shows frost in the alert's own night), `NotYet` (usable, but warm, outside the window or from another night) or `Unconfirmed`. Only `Confirmed` has an effect: `frost_payload_with_evidence` appends one factual sentence ("A nearby station read 1°C at 23:40.", local time, no operator named, no delivery promise) and the `Evidence` goes to the delivery log. The alert is never held back waiting for a confirmation, because dedupe sends one alert per night. The limits are ours (no standard names a representative radius for a frost reading) and deliberately tight; fit them against the recorded forecast verification once it exists. Fixtures only, no network, no clock (the caller passes `now` and the place's `utc_offset_seconds`).

**Reference data** (`mukoko-weather-api`, no binding): `GET /v1/activities` (`id`, `category`, `q`, `labels`, `mode=categories`), `/v1/suitability` (`key`), `/v1/tags` (`featured=true`), `/v1/regions`, `/v1/ai/prompts` (`key`) and `/v1/ai/suggested-rules`, with the shapes and ordering of the old `/api/py/*` routes (`weather_core::reference`). The Python backend read these from MongoDB, where `/api/db-init` had copied the app's seed files; the Workers hold no database connection (#150), so the same documents are compiled in from `crates/weather-core/data/reference/*.json`, generated by `scripts/gen-reference-data.mjs` (CI fails when they are stale). To change one, edit the seed file in `src/lib/`, run the generator, then `prettier --write` on the JSON. Differences from Python: text search is an OR of stemmed terms over label, description and category (the MongoDB text index's behaviour, not its scoring); the data-managed `aiInstructions` on an activity lived only in MongoDB and is not served; the `system:*` prompts are never served (the AI Worker has them compiled in).

**`mukoko-weather-places`** (service binding only, from `mukoko-weather-api` as `PLACES`) also serves the device preference profiles (`POST /v1/devices`, `GET` and `PATCH /v1/devices/{id}`, ported from `api/py/_devices.py`): one document per device in MongoDB (`device.device_profiles`), last write wins, written and read by `mukoko-weather-mongo-bridge` through the `MONGO_BRIDGE` service binding (never D1; **deploy the bridge before this Worker**), 20 new profiles an hour per client (D1 `rate_events`). It serves `/v1/locations`, `/v1/search`, `/v1/geo` and `/v1/history` with the parameters and shapes of the former `/api/py/locations|search|geo|history` (the Python routes, creation included, are deleted). It reads no database for places: the seed locations (with their tags) are compiled in; a `{name}--{geohash}` slug carries its own point (the app's smart slugs, which `mukoko-weather-forecast` now resolves too); canonical places come from the Nyuchi API (`/v1/places`, `/v1/places/nearby`, `/v1/places/{slug}`); geocoding comes from Open-Meteo (forward) and Nominatim (reverse, rate limited per client), all cached in KV. `geo?autoCreate=true` names the point and answers its `{name}--{geohash}` slug, but writes no canonical place; the named place carries `elevationApproximate: true` (its elevation is a placeholder 0), like a spot (`weather_core::resolve::point_body`). `search` tops a thin answer up from the geocoder and offers a country, province or continent itself as the LAST results (a spot at its centre, `area` set; a slot is reserved for it), after the places and the best cities of a country the query named, deduped against the seed list (`phuket-th`). `geo` never dead-ends: a seed within 150 km, else a spot named by a cached, budgeted city-level Nominatim lookup of the ~1 km cell, else a coordinate label spot (`12.35°N 45.62°E`). `named: false` means a definitive nothing here; `namingSkipped: true` (over budget, an outage, or `noName=1` from a server caller) says nothing about the point, is `no-store`, and `autoCreate=true` returns a seed within 50 km instead of a label when naming was skipped. Nominatim has its own hourly D1 budget (60/h per client, 3,000/h service-wide) besides the per-minute `GEOCODE_LIMITER`. Nothing is stored. `search?q=<name>&mode=resolve` is the one best place for a bare name in a URL (`/koh-samui`): the app's proxy 308-redirects to its `{name}--{geohash}` slug (`weather_core::resolve`; it stores nothing, and answers `resolve` = `ok` | `no_match` | `over_budget` | `unavailable`). Uncached forward geocodes spend an hourly budget kept in D1 `rate_events` (`weather_core::budget`; per client and service-wide; resolve and search are separate budgets, resolve 60/h per client and 150/h service-wide, search 120 and 350, so autocomplete cannot starve a bare-name resolve; it fails closed). The client key is a hash of a verified token subject when a verifier exists (none yet: the issuer is a platform responsibility, #148), else of the IP. Answers are cached in KV (hits a day, misses ten minutes; "nothing here" is stored as a `Slot`, never a bare `null`, which KV reads back as a miss); a budget, over-budget or outage answer is `no-store`. **`/v1/history`** (`GET ?location=` and/or `lat=&lon=`, `days=` 1..3660 or `start=&end=`; `src/history.rs`, rules in `weather_core::history`) reads our own store first and pulls ONLY the missing past dates from an external archive: the days `mukoko-weather-jobs` RECORDED (D1 `place_daily`, seed places), then MongoDB `weather.weather_history` through the bridge (the days the Python backend recorded until 2026-10-18 and every archive day), then NASA POWER and Open-Meteo's ERA5 archive (order `HISTORY_PROVIDERS`, default `nasa-power,open-meteo-archive`) for the rest: newest runs first, chunked to each provider's span, at most 6 upstream calls and 20 s a request, the fetched days written back through the bridge insert-only (`POST /history/days`) after the answer is sent (`wait_until`). Any coordinate on Earth works (a spot is stored under `geo:<geohash7>`, a bare coordinate under its 0.05° `cell:` key; both limited to the newest 366 days). Never fails the answer for a provider (it falls to the next, then to what is held; a bridge that is down means the fetched days are returned and not stored); a day carries `source` `recorded` | `nasa-power` | `open-meteo-archive` and the answer carries `sources` (attribution), `backfilled`, `missing`, `clamped`. D1 `rate_events` budgets: `history-backfill` 30/h per client (`history-backfill-coords` 10/h for a spot or bare coordinate; spent only when a call goes upstream), `history-nasa-power` 600 calls/h, and `history-open-meteo` in WEIGHTED units (a year of 19 variables is about 50 of Open-Meteo's own billing units; 250/h service-wide, 150/h per client, at most 150 units per request). When D1 or the bridge cannot be read nothing is fetched and the answer is `no-store` (`degraded: true`; so is any answer cut short by a spent budget, an open breaker, a provider failure or a cap while dates are still missing, and only a plain archive lag is cached, 60 s); it is a 502 only when no store was actually read; the fetched days are stored in the background (`saving: true`; a failed save logs the HTTP status and the bridge's error code). A place's days recorded under its platform slug (`nairobi-518dd4`) are merged in too: the bridge finds that slug in `places.placesGeo` (read-only) near the place's own point. A budget spend is one guarded D1 statement (the rows are inserted only if both hours have room, and the change count is the decision), so parallel requests cannot all pass. Provider chunks are cached 3 h in KV (`hist:v1:`). Optional config: vars `HISTORY_PROVIDERS`, `HISTORY_COMMERCIAL_ONLY` (`1` drops Open-Meteo unless the paid archive host is in use: its free host is non-commercial), `OPEN_METEO_ARCHIVE_LICENSED` and the Open-Meteo key (the same shared mechanism as the forecast Worker, see "Open-Meteo paid plan" below): the archive moves to `customer-archive-api.open-meteo.com` only with a key AND `OPEN_METEO_ARCHIVE_LICENSED=1`, so adding a Standard-plan key does not break history. Bindings: KV `CACHE` (the forecast namespace), D1 `WEATHER_DB` (reads `place_daily`, writes `rate_events`), service `MONGO_BRIDGE`, rate limit `GEOCODE_LIMITER`, secret `NYUCHI_API_KEY`, var `NYUCHI_API_URL`.

**Canonical slugs for the shipped seeds (#317).** Each of the 264 seed places has a legacy slug (`harare`, `nairobi-ke`) and a pinned canonical one (`harare--ksy4dd1`, `{name}--{geohash7}` of its own coordinate), in `crates/weather-core/data/slug-migration.json`, generated from `src/lib/slug-migration-data.ts` by `scripts/gen-seed-locations.mjs` (CI `--check`) and re-derived from the seed list by a native test. `weather_core::slug_migration` and `locations::find_seed` / `places::resolve_seed` accept BOTH spellings, so the places, forecast, ai and jobs Workers answer for a canonical slug as the seed it names (not as a bare spot: its own province, tags, height and recorded days). An answer keeps the spelling it was asked by, so nothing a caller already gets changes. A seed's stored data stays under its LEGACY slug (D1 `place_daily`, MongoDB reports and archive days: `community::storage_slug` / `read_keys`, `history::d1_slug`); a canonical seed slug also reads its `geo:<geohash7>` report cell key, never writes it. Only a slug in the table is touched: a community, platform or Nyuchi place keeps its slug, and `locations::slug_branch` (seed, then spot, then Nyuchi and community) never reads a slug without `--` as a spot. **Deploy these Workers before the app that sends canonical slugs:** an old Worker reads `harare--ksy4dd1` as a spot (history clamped to 366 days, no recorded days, the spot budgets, archive days under `geo:` keys the new Workers never read).

**Community reports on `mukoko-weather-places`** (`POST /v1/reports`, `GET /v1/reports?location=&hours=` and `POST /v1/reports/upvote`, `src/reports.rs`, ported from `api/py/_reports.py`; the rules are `weather_core::community`, pinned to what the Python stored by `tests/fixtures/report-submit.json`): a report is a document in MongoDB (`weather.weather_reports`), written and read by `mukoko-weather-mongo-bridge` through the `MONGO_BRIDGE` binding (never D1). A submission is validated here first (description at most 300 characters, one of 14 types, severity `moderate` unless `mild` or `severe`, coordinates on the globe when given), limited to 5 an hour per client (D1 `rate_events`, action `weather-report`; ONE guarded statement, `budget::SPEND_SQL`, so parallel requests cannot all pass; the client's hour is a `429`, and the service's hour or a budget D1 cannot read is a `503`: it fails closed), resolved to a place (the seed list, a `{name}--{geohash}` spot, a Nyuchi API place, or a community place from `places.placesGeo` found by the slug the app stamped on it (`sourceProvenance.mukokoSlug`, e.g. `windsor-avenue-zw`) through the bridge's read-only `GET /places?slug=`; a slug that resolves nowhere is a `404`, and a bridge that cannot answer is a `503`, never a `404`; a spot is stored by its `geo:<geohash7>` cell, never by the name half of its slug) and cross-validated against the conditions the forecast Worker already cached for that point (KV `wx:v2:`, read only: no provider call, no cost; no cached forecast means a report that cannot be verified; a `wildfire` report is NEVER verified, with or without a forecast: `weather_core::community::NEVER_VERIFIED` decides it before anything is read, and the bridge refuses a wildfire report marked verified, so it is only ever a community report, unverified). The reporter and an upvoter are the first 16 hex characters of the SHA-256 of their address. The list reads a slug and, for a spot, its cell, newest first, at most 20, `hours` clamped to 1..72. `POST /reports/clarify` (the model's follow-up questions) is not here: it is the AI Worker's (below). `mukoko-weather-api` relays all three to `PLACES` with the client's address, never cached.

**Developer keys.** `mukoko-weather-api` stays open to anonymous callers (600 a minute per IP, because a school or office shares one address). A developer may send a Nyuchi API key (`X-API-Key: nyk_….nys_…`, or `X-Client-Id` and `X-Client-Secret`) scoped for `weather`. The Worker keeps no key store: it forwards the key to the Nyuchi API's `GET /v1/weather/key`, which validates it, enforces the monthly quota and counts the call, and keeps a good answer in memory for 60 seconds (under a SHA-256 of the key), so usage is counted per check, not per request. A keyed caller is limited per key (`KEY_RATE_LIMITER`, 600 a minute). A bad key is `401`, a key without `weather` is `403`, and if the Nyuchi API cannot answer the call is refused with `503` (fail closed). Keys are created in the Nyuchi API (`POST /v1/api-keys`).

**Place knowledge** (`GET /v1/locations/profile?slug|lat&lon[&country]`: `mukoko-weather-forecast` `/profile`, relayed by `mukoko-weather-api`; `weather-core` `place_profile`, `climate_normals` and `ag_calendar`; ported from the Python route and pinned to it by `tests/fixtures/place-profile.json`) returns what we know about a place that changes slowly, with its source and licence per field, and `current` computed at read time. Nothing is stored. Three things differ from the Python, so read them before relying on the route:

- **No MongoDB.** The forecast Worker has no Mongo binding (no `MUKOKO_WEATHER_MONGODB_URI` in its `secrets_store_secrets`, and no plain `MONGODB_URI` secret unless the owner set one), so the Mongo season rows (`weather.seasons`, including the AI-made ones) and a stored neighbour's `placeKnowledge` are never read; both paths fall back and stay dead until the owner step in "MongoDB from a Worker" is done. A country missing from the compiled `crates/weather-core/data/seasons.json` gets a derived hemisphere or wet/dry calendar where the Python served the stored rows.
- **`place_near` knows only the seed places.** The nearest-place lookup searches the compiled-in seed places within 3 km (`NEAREST_PLACE_KM`), not `placesGeo`. A bare coordinate near an African town that is not a seed gets no country, so no GEOGLAM crop calendar and no season calendar, unless the caller passes `country` (the location page does). A place the Nyuchi API resolves has no province (`admin1`).
- **New KV keys, and the archive is fetched three times.** Soil and normals are cached under `soil:v1:` and `nrm:v1:`. The same 30-year ERA5 archive request is made separately by `/normals`, `/monthly-normals` and `/profile` for a cold 0.25° cell (up to three requests where the Python made one). All three sit behind the Open-Meteo breaker; only `/profile` is metered: 120 builds an hour per client and 600 service-wide (`Action::PlaceProfile`, D1 `rate_events`, no migration needed). The unit is taken only when an upstream call will really go out, so a request answered from KV, or one whose Open-Meteo or SoilGrids breaker is open, costs none.

**Open-Meteo paid plan** (`weather_core::open_meteo`, `weather_edge::open_meteo`; #434). The free Open-Meteo API is non-commercial and refuses the Workers' shared egress address with HTTP 429. With the key present, `forecast`, `places` (history) and `public-api` (the `/v1/status` probe) use the paid hosts; without it nothing changes. The key is the Secrets Store secret `OPEN_METEO_API_KEY` (created under that name), bound on those three Workers as `MUKOKO_WEATHER_OPEN_METEO_API_KEY` (`"secret_name": "OPEN_METEO_API_KEY"`); the code asks for it as `OPEN_METEO_API_KEY` through `weather_edge::secret`, so the plain-secret transition fallback applies to it too. A binding to a store secret that does not exist fails the deploy (error 10182), so the secret must exist before `forecast`, `places` or `public-api` deploys.

- **What moves.** `weather_edge::open_meteo::init(env)` runs at the top of the request in `forecast` (every route), `places` (history and `/health`) and `public-api` (`/v1/status`); `get_with_timeout` then rewrites every outbound URL on `api.open-meteo.com` to `customer-api.open-meteo.com` and on `air-quality-api.open-meteo.com` to `customer-air-quality-api.open-meteo.com`, appending `apikey=` (percent-encoded). That covers the blend, single model, `best_match` and extras, air quality and its grid, haze, agriculture, the model grid and the status probe, with no change at the call sites. Cache keys are built from coordinates, never from a URL, so they are unchanged.
- **The archive host is opt-in, and it is off.** `archive-api.open-meteo.com` (history in `places`, climate normals and the place profile in `forecast`) moves to `customer-archive-api.open-meteo.com` only with a key AND the Worker var `OPEN_METEO_ARCHIVE_LICENSED=1`; unset or `0`, it stays on the free host, key or no key. The owner's plan is the lowest tier and has no historical weather API (owner, 2026-11-05, correcting the licence confirmation of the same day), so `forecast` and `places` declare the var as `"0"` in their `wrangler.jsonc`. It is declared, not removed, because both Workers use `keep_vars`, which would keep a `"1"` already deployed. An archive call is therefore on the free host, which is non-commercial, exactly as before the paid plan. After an upgrade to a plan with the historical API, set the var to `"1"` on both Workers. A refused key (401, 402 or 403) on the customer host is repeated once on the free host and logged, so a wrong `"1"` costs a request, not the answer. `/health` on both Workers reports `open_meteo_commercial` and `open_meteo_archive`.
- **Left alone.** Geocoding (`geocoding-api.open-meteo.com`, which answers without a key) and every other host.
- **The key never leaves the Worker.** It is in the URL, so no keyed URL is logged, cached, stored or returned: error text from a failed call is masked (`weather_core::open_meteo::scrub`) before it leaves `get_with_timeout`, the history failure line is built by `history::failure_line` (provider, range, a fixed word or an HTTP status), and `/health` reports only booleans (`open_meteo_commercial`, `open_meteo_archive`). The browser never gets it: `src/lib/open-meteo-endpoint.ts` and the app are unchanged and no `NEXT_PUBLIC_*` variable exists for it.
- **Self-hosted Open-Meteo is still not supported.** Only the three commercial hosts above are mapped; a base URL for a self-hosted instance (`infra/open-meteo/`) is not threaded through the Workers.

**Deploy order against Vercel.** Every route is a Worker route now (the Python backend is deleted, #333) and the app calls `weather-api.mukoko.com` with **no fallback** (`src/lib/weather-api.ts`). A push to `main` that touches `workers/` deploys all the Workers (`workers-deploy.yml`, in the binding order below: `forecast` first, `public-api` last), and Vercel deploys the app from the same push, so for some minutes the new app can run against the previous Workers and the new Workers against the previous app. A route the app calls before it exists answers `404` and the card it feeds (for the profile route, the place-knowledge rows of the About card) renders nothing until the Workers are up. So release in two steps, expand then contract: ship the Worker change first, tolerated by the previous app, and the app change that uses it in a later release (or make the app degrade when the route is missing); remove a route or field from the app in one release and from the Workers in the next. A new binding, store secret or D1 migration must exist before the release that needs it: the deploy applies none of them. Rolling the Workers back past a ported route breaks the live app the same way, so roll Vercel back first. The full rules are in CONTRIBUTING.md, "Deploying the Workers".

## Shamwari Weather (the AI Worker)

```text
POST /internal/summary        {location: {slug, name, lat, lon, elevation, country, tags}, activities}
                              → {insight, cached, generatedAt}
                              (only from mukoko-weather-internal, for the signed-in app; not public)
POST /internal/followup       {message, locationName, locationSlug, weatherSummary, activities, season, history}
                              → {response}
                              (only from mukoko-weather-internal, for the signed-in app; not public)
POST /internal/agriculture    {location: {slug, name, country, elevation, lat, lon}, activities, mode: "snapshot" | "briefing"}
                              → {text, source, cached, mode, generatedAt}
                              (only from mukoko-weather-internal, for the signed-in app; not public)
POST /v1/ai/chat              {message, history, activities} → {response, references: [{slug, name, type}]}
POST /v1/ai/history/analyze   {location, days: 7..365, activities} → {analysis, stats, cached, dataPoints}
POST /v1/ai/explore/search    {query} → {locations: [{slug, name, province, country, tags, temperature?, weatherCode?, humidity?, windSpeed?}], summary, source: "ai" | "text"}
POST /v1/reports/clarify      {reportType, locationSlug?} → {questions: [one or two], source: "ai" | "fallback"}
```

- **Guardrails.** `GET {NYUCHI_API_URL}/v1/ai/guardrails/compiled?applies_to=weather` with `X-API-Key`. The block is used for 60 seconds, then revalidated with `If-None-Match`. If the API can't be reached, the last block is used for up to 24 hours. With no usable block every route answers `503 guardrails_unavailable`.
- **Model calls.** `env.AI.run(model, input, {gateway: {id: "shamwari", collectLog: false, metadata}})`. The metadata names the route only, never user content. A Guardrails or DLP block (2016, 2017, 2029, 2030) is answered with a polite refusal; a gateway rate limit with `429`.
- **Failed model calls are logged** (#416), one warn line each, so the cause is visible in Workers Observability instead of only a refusal or a fallback answer: `ai model call failed: route=explore class=blocked stage=rejected name=AiError code=2016 status=- finish=-`. `route` is the gateway metadata route (`summary`, `followup`, `chat`, `history`, `explore`, `backend`), `class` is `blocked` (Guardrails or DLP), `rate_limited`, `failed` or `empty` (the call answered with no text and no tool call), `stage` is where it went wrong (`binding`, `input`, `call`, `rejected`, `output`, `answer`), `name` is the JS error's class name, `code` the AI Gateway or Workers AI error code (the error's own leading number or the number after a `code` or `error` key, 3 to 5 digits in the ranges Cloudflare's codes use) and `status` a 4xx or 5xx HTTP status, each only when the error text names one, and `finish` the first choice's finish reason for an `empty` answer (`length` means the budget went on reasoning). The error text is only READ for the code and the status (`weather_core::ai::failure`, natively tested): the line never carries the message, a prompt, an answer or a key, and a number in a quoted prompt (a zip code, a card number) is not read as a code. Gateway codes: `2016` prompt blocked and `2017` response blocked by Guardrails (HTTP 424), `2029` and `2030` request and response blocked by DLP, `2003` rate limited (429), `2001` no gateway configured; Workers AI: `3040` capacity (429), `3036` daily free allocation (429), `5007` no such model. `class` comes from `is_content_block` and `is_rate_limited`, which match the digits anywhere in the error text: a `blocked` line whose `code` is none of 2016, 2017, 2029 or 2030 was matched by accident.
- **The summary** is a signed-in route of the app, not a public one (`weather_core::ai::summary` and `prompts`, pinned to the Python it replaced by `tests/fixtures/ai-summary.json`). The app's `/api/ai` proxy checks the WorkOS session, then calls `mukoko-weather-internal` `POST /internal/ai/summary` with the service key, `X-Mukoko-User-Id` and `X-Mukoko-Client-IP`; that Worker forwards to this one's `/internal/summary`. These paths have no public route and `mukoko-weather-api` forwards `/v1/ai/*` only, so the sign-in gate cannot be bypassed. The Worker fetches the weather itself from `forecast`; the `weatherData` a client sends is ignored. The prompt is the Python's byte for byte, except that a season whose local name is its English name is written once (`Season: Summer rains`, not `Season: Summer rains (Summer rains)`): the location, its tags, the user's activities (known ids only, at most three, with their labels and the per-activity guidance from `data/reference/activity-guidance.json`), the season (the country's calendar from the compiled seed, else the hemisphere's) and the place profile block (`forecast` `GET /profile/prompt`, cache-only, 4 s bound). The entry is cached in KV for 30 minutes for a `city`, 60 for a farming, mining, education or border place and 120 otherwise, under the place and the sorted activities (a seed city by its slug; anywhere else by the ~1 km cell and a hash of what the client said, so no caller reads another's text), and redone early when the temperature moves more than 5 degrees or the weather code changes. If the model fails, the plain-conditions text is served and cached for a minute. Only a call that goes to the model is counted: 30 an hour per person and 1,500 an hour for the service (D1 `rate_events`, action `ai-summary`, fails closed), answered `429` with `Retry-After` beyond that.
- **The follow-up** (`/internal/followup`) builds the Python's system prompt and message list (pinned by `tests/fixtures/ai-followup.json`): the location, the summary the user is asking about (as text in the prompt and as the first assistant message), the user's activities as ids, the season, and the place profile block for the page's slug (`profile::block_for_slug`, with the grounding rule). No cache: every message is a model call, counted against the person (`ai-followup`, 30 an hour, 1,500 an hour service-wide).
- **The agriculture explanation** (`/internal/agriculture`) asks the forecast Worker's `/agriculture` for the deterministic farm data and has the model explain it in one sentence (`snapshot`) or a briefing (`briefing`), with the user's farming activities and their guidance (`weather_core::ai::agriculture`, pinned by `tests/fixtures/ai-agriculture.json`). The entitlement hook (`weather.agri_insights`) runs before the KV cache is read; a hit is free; a miss is counted before the farm data is fetched, even when the answer ends up being the fallback text, so the hour also bounds the lookups a person causes (`ai-agriculture`, 30 an hour per person, 600 service-wide). Cached 1 h (60 s for fallback text) under the place, mode and sorted crops; the place part follows the summary's rule, so no caller reads text another caller steered. No farm data or no model answer serves the deterministic fallback text.
- **The chat** has no tools. The seed places named in the message (or, failing that, earlier in the conversation) are looked up first, up to three, and their forecasts go into the prompt. `references` lists them.
- **History** reads the same history the app shows, from `mukoko-weather-places` over the `PLACES` binding (recorded days, stored archive days, and an archive fetch for the rest), for `days` 7..3660 or `start`/`end`. No rows gives `404 no_history`; the places Worker not answering gives `502 history_unavailable`. Analyses are cached for an hour, keyed on the data. The statistics text the model reads (`weather_core::ai::history::aggregate`) is pinned to the former Python's `_aggregate_stats` by `tests/fixtures/history-analysis-stats.json`, down to how Python prints an integer (`20`) against a float (`20.0`) and rounds a tie; days from an archive (`open-meteo-archive`, `nasa-power`) are named in the text so the model does not read the mix as a trend. The message also carries the place-profile block and its grounding rule (`profile::block`, cache-only and bounded at 4 s, no profile is no block), as the Python's did; `tests/fixtures/ai-place-profile.json` pins the message to the real Python.
- **The AI search** (`/v1/ai/explore/search`, ported from the Python `_explore_search.py`, pinned to it by `tests/fixtures/explore-search.json`) gives the model two tools and up to three rounds: `search_locations` over the compiled-in seed places (name or province contains the text, or the tag matches; 20 at most) and `get_weather`, one `current` block from the forecast Worker (`FORECAST` binding; at most eight lookups a search, a limit the Python did not need because it read only the MongoDB cache). The answer is up to ten places and the model's last text. When the model cannot answer (no guardrails block, the service's hour is spent, a model error or a gateway block) the answer is the plain text match with the cached weather of each place (`source: "text"`), as the Python's was; a query with email, phone or card numbers is refused (`422`).
- **The report follow-up questions** (`POST /v1/reports/clarify`, `src/clarify.rs`, rules in `weather_core::ai::clarify`, ported from `clarify_report` in the former `api/py/_reports.py` and pinned to it by `tests/fixtures/report-clarify.json`, which the (since deleted) `scripts/gen_report_clarify_fixtures.py` produced from a pinned commit of the real Python) is the report wizard's optional step, so it never fails a visitor: a valid request (`{reportType, locationSlug?}`: one of the 14 types and, when given, a slug; 1 KiB at most) always gets `200` with the model's one or two questions or the fixed pair for the type (`source: "fallback"`). The pair answers when the guardrails block is missing (this route does not `503` like the others), the client's hour (10) or the service's hour (600, `ai-report-clarify`) is spent, the budget cannot be read (it fails closed), the personal-data check trips, the model fails, is blocked or answers nothing usable, or takes more than 8 s. Nothing a visitor types reaches the prompt: the place is named from the slug (the seed catalogue, else the name part of a `{name}--{cell or map ref}` slug or the slug's words, never an id or hash; "your area" with no slug) and the type is allowlisted, so there is no text to store, screen or log; a failed call logs route, class and stage only. The prompt is the seeded `system:report_clarification`. `mukoko-weather-api` forwards it as a first-party POST (`weather_core::ai::is_forwarded_path`): the listed app origins may call it from the browser, a foreign website may not (`weather_core::cors`). **Deploy `ai` before `public-api`.**
- **Budgets for the model calls** (`weather_core::budget`, D1 `rate_events` through the `WEATHER_DB` binding, the table the places and stations Workers already use; no migration): the search 15 an hour per client and 600 service-wide (`ai-explore-search`), the history analysis 10 an hour per client and 300 service-wide (`ai-history-analysis`), the Python's limits. One guarded statement spends the unit or refuses (`SPEND_SQL`); the budget fails CLOSED. A client over its hour gets `429` with `Retry-After`; the service's hour spent, or a budget that cannot be read, answers the search from the text match and the analysis with its statistics alone, never from the model. An analysis answered from the cache costs nothing. A client is the SHA-256 of the visitor's address (`CF-Connecting-IP`, else the `X-Mukoko-Client-IP` that `mukoko-weather-api` now stamps on the forward), never the address itself. Deploy `ai` (it carries the new binding), then `public-api` (the new header); nothing else changes.

- **The backend passthrough.** `POST /internal/chat/completions` takes an OpenAI chat-completions body (`messages`, `tools`, `max_tokens`, optional `model`) from the Python backend, through `mukoko-weather-internal` (which checks `WEATHER_SERVICE_API_KEY`; `mukoko-weather-api` never forwards this path). **Its only known caller, the Python backend, is deleted; nothing in this repository calls it, and it stays until its other possible callers are ruled out, then it goes (a Worker change: `ai` and `internal-api`).** It rebuilds the messages from known keys, puts the guardrails first in the one system message, refuses user turns with personal data (`422`), runs `env.AI.run` through the gateway with any `tools`, and answers an OpenAI chat completion with `content` only (never `reasoning_content`) and OpenAI-shaped `tool_calls`, so the Python tool loops are unchanged. No per-IP limit here (every backend call shares one key); the backend limits per visitor. Logic: `weather-core/src/ai/completions.rs`.
- **The model and its budget.** `AI_MODEL` is `@cf/zai-org/glm-5.3-flash` (Z.ai GLM-5.3 Flash: function calling and reasoning). Only GLM ids (`@cf/zai-org/glm-…`) are accepted (`allowed_model`, owner 2026-11-05: Shamwari and every other model call run GLM models only), from the `AI_MODEL` var and from a caller of the passthrough alike; anything else falls back to the default, `weather_core::ai::DEFAULT_MODEL`. For reasoning models every call adds `REASONING_HEADROOM` (1024) to `max_tokens` and sends `reasoning_effort: "low"`; GLM cannot switch reasoning off, and an answer whose budget went on reasoning comes back empty (`502 model_failed`).

Not ported from the Python backend: the chat's tool loop (search beyond the seed places, places by tag), the AI search's reach beyond the seed places (the Python listed `placesGeo`, which the Workers do not read) and the AI-made season rows in MongoDB `weather.seasons` (a country the compiled seed lacks gets the hemisphere's season). The prompts are compiled in (`weather-core/src/ai/prompts.rs`); the per-activity guidance (`aiInstructions`) is a snapshot of the 55 production documents taken on 2026-11-01, so editing it in MongoDB no longer reaches the model.

## The internal forecast contract

This is the upstream for the Nyuchi API's `GET /v1/weather/forecast` (nyuchi/api-gateway#154). The Nyuchi API needs two settings:

- `WEATHER_SERVICE_URL=https://weather-internal.mukoko.com`;
- `WEATHER_SERVICE_API_KEY`, set to the same value as this Worker's secret.

```text
GET /internal/forecast?location=<slug|name>        (or lat=&lon=)   [&days=1..7, default 7]
Authorization: Bearer <WEATHER_SERVICE_API_KEY>

200 {"location": {"slug", "name", "lat", "lon"},
     "data": [{"date": "YYYY-MM-DD", "description", "weather_code", "high", "low",
               "precipitation_probability"}],
     "source": "tomorrow" | "open-meteo",
     "fetched_at": "RFC 3339",
     "attribution": "provider credit line"}
401 missing or wrong key       404 unknown location     422 bad query
503 no key configured here, or no provider answered (fails closed)
```

**How a place is resolved.** Locations resolve in this order:

1. the app's seed locations (compiled in), matched by slug, by name, or by the name's slug;
2. the Nyuchi API (`GET /v1/places/{slug}`, cached), because canonical place records belong to the API;
3. otherwise `404`.

**Requests by point.** A `lat`/`lon` request borrows the slug and name of a seed location within 10 km. Otherwise the slug is the rounded point and the name is `null`.

## Station import (B3, [#561](https://github.com/mukoko-dev/mukoko-weather/issues/561))

Moves the stations in MongoDB `weather.stations`, with their key hashes unchanged, into the Nyuchi API (`device.devices` and `device.ingest_credentials`), so every console already in the field authenticates there. It has to be done before `STATIONS_BACKEND` is flipped to `nyuchi` ("Station backend cutover" below): the API rejects a key for a station it does not hold. The D1 path (`scripts/stations-to-d1.mjs`, `d1/migrations/0001_stations.sql`) is untouched and is what runs while `STATIONS_BACKEND=d1`.

**Two tools, built and tested; no agent has run either against production. You run them.** The commands below were checked against the code and the API's tests, on fake data. The `wrangler dev` replay (step 9) and the `curl` calls have **not been run** against a live Worker or the live API: read each once before you paste it.

- `workers/scripts/stations-to-devices.mjs` (this repo): reads an owner-run `mongoexport --jsonArray` of `weather.stations` and writes batch files for the route. A pure transform: it connects to nothing and prints only counts and masked ids (`mws-0a****3d`), never a hash, a salt or a name. Tests: `node --test workers/scripts/stations-to-devices.test.mjs`.
- `POST /v1/stations/import` on the Nyuchi API ([nyuchi/nyuchi-api#544](https://github.com/nyuchi/nyuchi-api/pull/544); the text is `docs/architecture/stations.md` there).

**What the import does.** Each station becomes a `device.devices` document owned by the community until a person claims it (owner decision O-S3), with its PBKDF2 hash and salt stored exactly as exported (`pbkdf2-sha256-60000`), so the key in the field keeps working, and one `registered` history event (`system_migration`). It is **safe to repeat**: a station already imported is `unchanged`, an existing credential is never replaced (a key an owner rotated since is not put back), a station a person has claimed is never touched, and `isActive` is only set on creation. **A request that does not say `dryRun` is a dry run**; send `"dryRun": false` to write. One bad station is a result (`rejected`, with the field names), never an error, so it cannot stop its batch. It does **not** create the `community` entity record `COMMUNITY_OWNER_ID` names (nothing reads it; see the API's docs).

**Before you start:**

- The Nyuchi API is deployed with the station routes (nyuchi/nyuchi-api#313) and #544, and its declared indexes are applied (`python -m gateway.lib.indexes --apply`). Until `device.ingest_credentials` exists the route answers `503`, even for a dry run.
- You have `mongoexport`, `node` 22 or later, `jq` and `curl` (7.76 or later for `--fail-with-body`).
- A person who manages the workspace that owns the Worker's key **and holds the WorkOS permission `console:api-keys-mint`** mints the import key. It is its own key: scopes `stations` and `stations:import`, nothing else, a one-day expiry. **Never give it to the Worker, and never add `stations:import` to the Worker's key** (the route refuses a key that holds both). The exact request is in nyuchi/nyuchi-api#544.

**Steps, in order:**

1. **Snapshot first.** In MongoDB Atlas take an on-demand snapshot of the cluster that holds the `weather` and `device` databases, and wait until it shows as completed. Do not go on without it.

2. **Export, into a private directory outside the repo** (the export holds key hashes):

   ```bash
   umask 077
   WORK="$(mktemp -d)"
   mongoexport --uri "$MONGODB_URI" --db weather --collection stations --jsonArray --out "$WORK/stations.json"
   jq length "$WORK/stations.json"                                   # documents
   jq '[.[] | select(.stationId and .ingestKeyHash)] | length' "$WORK/stations.json"   # with an id and a key
   ```

3. **Transform** (from the repo root):

   ```bash
   node workers/scripts/stations-to-devices.mjs "$WORK/stations.json" --out "$WORK/batches"
   ```

   Read what it prints. `importable` should be the second count above; any difference is in `skipped`. `no_station_id` for the StationKit seed document (it has no key) is expected; any other `skipped` reason names the station (masked), so look that document up in Atlas and understand it before going on. The "set aside" line lists optional values (an impossible elevation, a future date) dropped so that a station keeps its key. The files are `stations-import-001.json`, ... of up to 50 stations, readable by you alone. Use a new directory for every run.

4. **Set up the call.** Keep the key out of your shell history and out of `ps`:

   ```bash
   set -o pipefail                       # a failed call must stop a loop
   API=https://api.nyuchi.com
   read -r  -p "import key client id: " IMPORT_ID
   read -rs -p "import key secret: "    IMPORT_SECRET; echo
   printf 'X-Client-Id: %s\nX-Client-Secret: %s\n' "$IMPORT_ID" "$IMPORT_SECRET" > "$WORK/auth.hdr"
   post() {   # $1 batch file, $2 true (dry run) or false (write)
     jq --argjson dry "$2" '. + {dryRun: $dry}' "$1" |
       curl -sS --fail-with-body -X POST "$API/v1/stations/import" \
         -H @"$WORK/auth.hdr" -H "Content-Type: application/json" --data-binary @-
   }
   ```

5. **Dry run every batch.** Nothing is written.

   ```bash
   for f in "$WORK"/batches/stations-import-*.json; do
     post "$f" true | tee -a "$WORK/dry.log" | jq -c '{dryRun, created, updated, unchanged, rejected}' || break
   done
   ```

   A line of `null`s means the call failed: its problem document is at the end of `$WORK/dry.log`. Expect `"dryRun":true`, `created` adding up to `importable`, and `rejected` 0. To see a rejection (index, station id, code and field names; never a value): `post "$f" true | jq '.results[] | select(.status=="rejected")'`. Fix the cause at the source, then export and transform again into a new directory. A `401` or `403` is the key (scopes, expiry); a `503` is the API not being ready (indexes, store).

6. **Import**, stopping at the first failure:

   ```bash
   for f in "$WORK"/batches/stations-import-*.json; do
     post "$f" false | tee -a "$WORK/import.log" | jq -c '{dryRun, created, updated, unchanged, rejected}' || break
   done
   ```

   `"dryRun":false`, and again `null`s mean the call failed (see the end of `$WORK/import.log`). A `503` (or a dropped connection) is safe to answer by running **the same batch again**: the import completes whatever the first attempt left half done (`updated`).

7. **Prove it is complete.** Run step 5 again. Every item is now `unchanged`: `created` 0, `updated` 0, `rejected` 0.

8. **Verify one station with its existing key.** Pick a station whose key you can lay your hands on (its console's `PASSWORD`, or the part of `PASSKEY` after the colon):

   ```bash
   ID=mws-xxxxxxxx
   read -rs -p "that station's key: " STATION_KEY; echo
   curl -sS "$API/v1/stations/$ID" -H "Authorization: Bearer $STATION_KEY" | jq '{stationId, name, status, lastSeenAt}'
   ```

   Expect `"status": "active"`. A wrong key is `401 invalid_credentials`. This is the same check the Worker will make through `POST /v1/stations/service/verify`, which you can run too with the Worker's own key (`WORKER_KEY`, `nyk_….nys_…`): `jq -n --arg id "$ID" --arg key "$STATION_KEY" '{stationId: $id, key: $key}' | curl -sS -X POST "$API/v1/stations/service/verify" -H "X-API-Key: $WORKER_KEY" -H "Content-Type: application/json" --data-binary @- | jq '{valid, station: .station.stationId}'` answers `"valid": true`.

9. **Shadow check: replay one legacy Wunderground and one Ecowitt payload** through the stations Worker in `nyuchi` mode **locally**, so production stays on `d1`. It needs Rust and `worker-build` (`cargo install worker-build@^0.8`; the `build` command in `wrangler.jsonc` runs it). It writes **one real observation per replay** for the station you pick, so use a station you own or accept the extra point.

   ```bash
   cd workers/stations
   printf 'NYUCHI_STATIONS_API_KEY=%s\n' "$WORKER_KEY" > .dev.vars     # git-ignored; delete it afterwards
   npx wrangler dev --var STATIONS_BACKEND:nyuchi --var NYUCHI_API_URL:https://api.nyuchi.com
   ```

   In a second terminal (the port is the one `wrangler dev` prints; 8787 is its default):

   ```bash
   # Wunderground: GET, imperial units
   curl -i -G http://127.0.0.1:8787/stations/ingest \
     --data-urlencode "ID=$ID" --data-urlencode "PASSWORD=$STATION_KEY" \
     -d tempf=70.52 -d humidity=45 -d baromin=29.92 -d windspeedmph=5 -d winddir=90 -d UV=3 -d solarradiation=500
   # Ecowitt: POST, form fields, PASSKEY=<stationId>:<key>
   curl -i -X POST http://127.0.0.1:8787/stations/ingest \
     --data-urlencode "PASSKEY=$ID:$STATION_KEY" \
     -d tempf=70.52 -d humidity=45 -d baromrelin=29.92 -d windspeedmph=5 -d winddir=90 -d uv=3 -d solarradiation=500
   ```

   Both answer `200` with the literal body `success`, as the Python route did. A wrong key answers `401 unauthorized`. Then, within a minute (the queue batches every 10 seconds at most):

   ```bash
   curl -sS "$API/v1/stations/$ID" -H "Authorization: Bearer $STATION_KEY" | jq '{lastSeenAt, lastObservationAt, latestMetrics}'
   ```

   `latestMetrics` should read about `airTemperatureCelsius` 21.4, `relativeHumidityPercent` 45, `atmosphericPressureMillibar` 1013.21, `windSpeedKph` 8.05, `uvIndex` 3, `solarRadiationWm2` 500 (the Worker's own unit conversions of the payload above). Stop `wrangler dev` and `rm .dev.vars`. If the Wunderground or Ecowitt answer differs from the old behaviour, **stop here**: do not flip.

10. **Clean up.** Revoke the import key (`DELETE /v1/api-keys/{key_id}`, or in the console), then `rm -rf "$WORK"`. The export and the batch files hold the key hashes.

11. **Flip** `STATIONS_BACKEND` to `nyuchi`: "Owner-only steps, in order" under "Station backend cutover" below (the Worker's own key, the secret, the flip, the checks, the forecast Worker). Your own station's real upload answering `success` and moving `lastSeenAt` at the API is the check that matters.

**Rolling back** is setting both vars back to `d1` and releasing (see the cutover section). The import is additive and idempotent, so nothing needs undoing: the imported stations are inert until the flip, and a later run changes nothing. **Be clear what `d1` means today:** production D1 holds 0 stations, so on `d1` no station authenticates, exactly as before this work. If you want a working fallback while you are on `d1`, also load D1 from the same export with the old path (steps 1 to 4 of "Station cutover" under "Owner steps"; `stations-to-d1.mjs` is kept for this). Do that before the flip, not after.

## Station backend cutover (B2, [#556](https://github.com/mukoko-dev/mukoko-weather/issues/556))

`mukoko-weather-stations` and `mukoko-weather-forecast` each have a var `STATIONS_BACKEND`:

- **`d1`** (the default, set in both `wrangler.jsonc` files): the Worker's own D1 registry and tables, exactly how it has always worked.
- **`nyuchi`**: the Nyuchi API (`/v1/stations/service/verify` and `/observations`, [nyuchi/nyuchi-api#542](https://github.com/nyuchi/nyuchi-api/pull/542); the text is `docs/architecture/stations.md` there) holds the stations and their readings.

A Worker that verifies keys against an API that does not hold the stations yet rejects every real station, so **nothing flips until the owner does it**. A value that is neither `d1` nor `nyuchi` fails closed (the stations Worker answers `503`, the forecast Worker serves no overlay) and logs an `ALERT`, rather than guessing.

**What `nyuchi` mode changes**

- `GET/POST /stations/ingest`: the same hot path (authenticate, QC, queue, `success`). The key is checked by the API; the isolate keeps a good answer for 10 minutes and a bad one for 60 seconds, under a SHA-256 of the station id and the key (never the key). An API that cannot answer, with a cold cache, is `503` with `Retry-After`, **never `401`**. Only `valid: false` is `401`. A `401` or `403` from the API means the Worker's own key was refused: the stations get `503` and the Worker logs `ALERT stations_api_credential_rejected`.
- The consumer sends each batch to `POST /v1/stations/service/observations` (at most 500 items per call; the API runs QC again, derives the ids so a retry stores nothing twice, and moves `lastSeenAt`), then folds the latest validated observation per station into the KV key `stations:latest`, then archives the raw uploads to R2 as before. An API failure retries the batch after 30 seconds; with `max_retries` 10, an outage of more than about five minutes sends the batch to `weather-observations-dlq`, which has no consumer (the messages stay there for the queue's retention; replaying them is a manual step).
- `POST /stations/register` answers `410` pointing to the console (anonymous registration ended).
- `POST /stations/manual` and `GET /stations/status` are thin proxies to the API's `POST /v1/stations/{id}/readings` and `GET /v1/stations/{id}`, with the station's own key as the bearer. The answers keep the shape legacy clients read. A manual reading no longer goes through the queue: it is not archived to R2, its note is not kept, and it is not in `stations:latest` until the API has a route for that ([nyuchi/nyuchi-api#543](https://github.com/nyuchi/nyuchi-api/issues/543)).
- D1 is no longer written for stations or observations. `rate_events` (the per-client limit on `manual`) still is. Retiring the D1 tables is a later change, after the cutover. The `jobs` Worker's `station_daily` rollup reads D1 `observations`, so it stops getting new days in `nyuchi` mode until that moves behind the API too (#293, Part 5.4 item 5).
- The forecast Worker reads `stations:latest` instead of D1: within 50 km and 60 minutes, the freshest wins (the D1 reader's rule). It lives in the forecast Worker's KV namespace under its own key, so there is no new store. The key is written by a read-modify-write, and KV is eventually consistent across locations, so two consumers can overwrite each other; a station missing from it comes back with its next upload. That is not measured. A refresh from the API would remove the problem (nyuchi/nyuchi-api#543). The forecast Worker keeps the parsed value for 30 seconds in each isolate (at 1,000 to 2,000 stations it is a few hundred kilobytes).

**Owner-only steps, in order** (an agent builds and tests; these are the owner's)

1. In the Nyuchi API (nyuchi/nyuchi-api#313): apply the declared indexes, deploy the station routes, mint the Worker's internal key with the scopes `stations` and `stations:service`.
2. Import the stations with their existing key hashes (B3, ["Station import"](#station-import-b3-561) above, steps 1 to 10), so every key already in the field verifies at the API.
3. Create the secret: the Secrets Store entry `MUKOKO_WEATHER_NYUCHI_STATIONS_API_KEY` (step 2 of "Owner steps"), or, until then, the plain Worker secret: `npx wrangler secret put NYUCHI_STATIONS_API_KEY -c stations/wrangler.jsonc`. The code reads either.
4. Bind the store secret (once it exists): add a `secrets_store_secrets` entry to `stations/wrangler.jsonc` and list `"stations"` in that secret's `workers` in `crates/weather-core/src/secrets.rs` in the same change (a test holds the two together). Not before the secret exists: Cloudflare refuses the deploy, and `workers-deploy.yml` deploys every Worker after this one.
5. Flip the stations Worker: set `STATIONS_BACKEND` to `"nyuchi"` in `stations/wrangler.jsonc` and release. The value in the file is what a deploy sets, so this line is the flip, and setting it back to `"d1"` is the rollback.
6. Check: `curl -s https://weather-ingest.nyuchi.com/health` shows `"backend":"nyuchi"` and `"status":"ok"` (`"misconfigured"` means something it needs is missing; which, is in the `ALERT` log line, not in this public body); a wrong key is `401`; a real station's upload answers `success` and its `lastSeenAt` moves at the API; `stations:latest` fills within a minute or two of uploads.
7. Then flip the forecast Worker the same way (`forecast/wrangler.jsonc`), and check `configured.stations_backend` in its `/health`.
8. Put a Cloudflare rate-limiting rule on the ingest paths of `weather-ingest.nyuchi.com` (per client IP; a station uploads at most a few times a minute, so tune it to the most stations behind one address). In `nyuchi` mode every key the Worker has not seen costs a call to the API, which the Worker does not limit per client; the API's ceiling for this key (6,000 requests a minute) is the only bound until the rule exists. The plan already puts the edge rules for these paths with the owner (#293, Part 5.6).

**Rolling back** is setting both vars back to `d1` and releasing. A station that exists only at the API is unknown to D1 and gets `401` in `d1` mode, and queued messages for it fail D1's foreign key until the dead-letter queue takes them.

**Log lines to alert on** (`console.error`, each at most once per 30 seconds per isolate): `stations_backend_misconfigured` (a missing API URL, key or KV binding: names only), `stations_api_credential_rejected` (the API refused the Worker's own key), `stations_api_contract` (an answer this code does not understand, for example the station routes not deployed), `stations_backend_unknown` (a bad `STATIONS_BACKEND`), `stations_latest_unavailable` and `stations_latest_unreadable` (the blend snapshot). Warnings: `stations_api_unavailable` (an outage; stations get `503`), `stations_latest_read_failed` and `stations_latest_write_failed` (the snapshot is derived; the next batch writes it again).

## Web Push alerts ([#289](https://github.com/mukoko-dev/mukoko-weather/issues/289))

Frost first, then severe weather, as Web Push to a browser that opted in. **Built:** the rules of what to send (`weather_core::push`: validation of an endpoint against an allow list, preferences, quiet hours, per-day and per-night caps, dedupe, the frost evaluation, the payload, what a push service's status means) and the protocol that carries a decided alert (`crates/weather-webpush`). **Built, dark:** the Workers-runtime half, `workers/push` (`mukoko-weather-push`, below). **Built, pure:** the planning half of the evaluator tick, `weather_core::alert_plan` (below), and the rules for severe-weather alerts from an official CAP source, `weather_core::severe_alert` (below). **Not built:** the evaluator tick itself in `mukoko-weather-jobs` (reading the forecast, asking the Nyuchi API for targets, claiming the alert in the delivery log, sending) and the VAPID key pair; nothing in this repo can send a push yet. (The Nyuchi API routes that store subscriptions, preferences and the delivery log, `/v1/notifications/*`, are nyuchi/nyuchi-api.)

`weather-webpush` is pure like `weather-core`: it holds no key, reads no clock, draws no random number, does no elliptic-curve arithmetic and opens no connection. The runtime injects each of those through three small traits and two arguments:

- `Transport`: the POST (a Worker wraps `fetch`, without following redirects).
- `Es256Signer`: the ES256 signature of the VAPID token. It owns the private key (a WebCrypto key imported from a secret binding), returns the raw 64-octet `r || s`, and reports the public key.
- `KeyAgreement`: a fresh ephemeral P-256 key pair and the ECDH shared secret with the browser's key, rejecting a point that is not on the curve.
- The current time and the 16-byte per-message salt (`crypto.getRandomValues`) are arguments.

**No Rust elliptic-curve crate is used.** RustCrypto's `p256` 0.13 resolves `crypto-bigint` 0.5, which `cargo audit` reports as RUSTSEC-2026-0387 (timing variability in operations meant to be constant-time; fixed only in 0.7.6, which that chain does not accept), and a security finding stays open until the owner decides. `KeyAgreement` and `Es256Signer` are the Workers runtime's own WebCrypto (`crypto.subtle`: `generateKey` and `deriveBits` with ECDH P-256, `sign` with ECDSA P-256 SHA-256, whose output is already `r || s`), which is native code and adds no crate; they are in `workers/push` (below), dark. What stays in the crate is everything deterministic: the HKDF-SHA-256 key derivation and the AES-128-GCM record (`hkdf`, `aes-gcm`: no advisory), the header, the JWT, the request. It builds for `wasm32-unknown-unknown` with no JS shim and tests natively on the RFCs' own vectors.

| Module    | Standard                                                                        | Pinned by                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `encrypt` | RFC 8291 message encryption over the RFC 8188 `aes128gcm` content coding        | the RFC 8291 section 5 worked example, byte for byte, from the RFC's own ECDH secret and public key (its printed `Content-Length: 145` is off by one; the body is 144 octets)           |
| `vapid`   | RFC 8292 voluntary application server identification (ES256 JWT, `vapid t=,k=`) | the RFC 8292 section 2.4 JWT signing input, byte for byte; the signer sees exactly `header.claims`; claims in the RFC's order; 12 hour expiry; the audience only ever an allowed origin |
| `request` | RFC 8030 (`TTL`, `Urgency`, the encrypted body) and the injected `Transport`    | headers, the audience being the push service origin, build errors that say whose fault they are, a full decrypt of the built request                                                    |
| `runtime` | the rules the Workers-runtime half must honour (not a standard of its own)      | the request check (https, a push service, five headers, one record, a bounded deadline), `Retry-After` for 429 and 5xx only, WebCrypto byte shapes, the VAPID JWK, the tripwires        |

Safety properties the tests hold: an endpoint outside the allow list (`weather_core::push::validate_endpoint`: https, a known push service, the default port only, no credentials) is refused before anything is signed or encrypted, so the sender cannot be pointed at an internal address, and a VAPID token is only ever made for an allowed origin; `Debug` of a request, a subscription, a recipient or an agreement never prints the endpoint, a key, a token or a body (an endpoint is a bearer capability; logs carry `weather_core::push::endpoint_id`, a SHA-256); a push service's answer is classified by `weather_core::push::classify_status` (a 404, 410 or 403 deactivates the subscription, a 429, 5xx or a timeout is retried on a later tick, any other 4xx is not), and `Outcome::delivery_status` maps it onto the `platform.alertDeliveries.status` values of the data-infra model. Delivery is best effort and nothing here promises it.

**The delivery claim and what a batch may deactivate** (`weather_core::alert_delivery`, step d, the pure half; no I/O). `read_claim` reads the Nyuchi API's answer to a claim (`POST /v1/notifications/alerts/deliveries` with status `queued`) and fails closed: only a `201` whose body says `created` and `queued`, or a `200` that says `updated` and `queued` (a retryable failure claimed again), is `Won` and may send. A repeat, a finished alert, a `2xx` whose body is missing or says anything else is `Held`; a `409`, `408`, `429`, `5xx` or no answer is `Retry` (the next tick plans the same key again); everything else is `Refused`. A test walks every HTTP status from 0 to 599 against every body shape and requires exactly those two to send. `plan_deactivations` turns a batch of send results into the explicit lists for `POST /subscriptions/deactivate`: only `Expired` results (404, 410, and a 403 for a key mismatch) are candidates, a subscription is named once, ids that fail the opaque id check are counted and never copied, and a call holds at most 100 (the API's limit). A wrong or rotated VAPID key, a wrong audience for one service, or a clock far off, makes a push service answer 403 to every send it gets, which is an operator problem and not a thousand people who left: judged per push service (each result carries its service's origin), a service that was sent at least three distinct subscriptions and refused all of them as `Expired` has none of them deactivated and the count is reported, whatever another service accepted (below three, a lone gone subscription is believed, and a service that accepted some of its own sends is believed, since after a key rotation the old subscriptions are refused for ever while new ones work; the three is ours and untuned). A subscription reported more than once counts once. **Known limit: at most once.** A sender that dies between winning a claim and logging an outcome leaves the row `queued`, which is not claimable again, so that person misses that night's alert; closing it needs the Nyuchi API to re-lease a `queued` row held too long (tracked on #289). Nothing here calls the API or a push service.

**The frost plan** (`weather_core::alert_plan`, step d, the pure half): what one evaluation tick does for one place, with no I/O, no clock (the caller passes `now` and the place's `utc_offset_seconds`), no binding and no key, so it cannot send anything. `plan_frost(place, targets)` takes the forecast series, its `X-Weather-Provider`, the place's slug, display name and `cell_key`, optionally the registered stations' readings, and a list of opaque alert targets (an id, the person's `AlertPrefs`, whether the subscription is active, and the counts sent today and tonight), and returns one entry per distinct target, sorted by id: a `PlannedSend` (the `{cell}:frost:{night}` dedupe key and the `Payload`) or the `Skip` reason (`no_frost`, `estimate_provider`, `invalid_place`, `inactive`, `bad_preferences`, `not_wanted`, `stale`, `already_sent`, `daily_cap`, `night_cap`, `quiet_hours`, `duplicate_target`, `tick_limit`). `assess_place` is the first half on its own, so a tick can skip fetching targets when the forecast shows no frost. Nothing is decided twice: the alert is `push::evaluate_frost` (never from a seasonal estimate), a station can only add the one sentence of `station_alert` to an alert that exists, and what to do with each person is `push::decide` (preferences, staleness, dedupe, caps, quiet hours, in that order; a severe frost still skips quiet hours, never the caps). The plan adds only what those do not know: an inactive subscription is never planned, a malformed preference record or place sends nothing, a target id given twice gets nothing (order independent), at most 1,000 targets are planned and at most 200 sends per place per tick (a target past the send limit is `tick_limit` and is planned again on the next tick, where those already sent no longer take a slot; both bounds are ours and untuned). Planning the same inputs twice, in any order, gives the same plan, and the key depends on the cell, the kind and the night only, so every tick of one night names the same key. **The key has exactly three `:` parts** (`-17.85_31.05:frost:2026-07-10`), which is what the Nyuchi API's delivery log requires (`validate_delivery`): `push::dedupe_key` drops the `cell:` prefix of `geo::cell_key`, because with it the key had four parts and the log would have refused every claim as `delivery_invalid` (found in code review of the severe-alert rules, 2026-11-04, before anything was sent); a test builds keys from real cell keys and pins the three parts. **The plan is not what stops a second push: the delivery log is.** A `PlannedSend` only authorises an attempt to claim its `dedupe_key`, and a send happens only after that claim is won (a 201 `created`, or a 200 `updated` whose status is `queued`); that rule is `alert_delivery::read_claim`, below. A target is an opaque id of `[A-Za-z0-9_-]` (pass `push::endpoint_id`, never the endpoint), and an id that does not fit is counted in `invalid_targets` and never copied into the plan, which never echoes a target's preferences. Each `PlannedSend` also carries the push's `PushOptions` (`push::frost_push_options`, RFC 8030): a `TTL` that ends the message where `push::decide` stops sending it (09:00 local the next morning for severe frost, midnight for moderate and high frost, since their copy says "tonight"; at most 36 hours, which the 24-hour forecast lookahead plus an 11-hour night never reaches), `Urgency: high` for severe frost and `normal` for moderate and high frost (only severe frost asks to wake a sleeping device), and a `Topic` of the kind and the night, such as `frost-2026-07-10`, so a retry replaces a copy a push service still holds. The topic holds no place, cell or person and no hash of one: the cell grid is public, so a hash of it would let a push service read the place back. A later tick of the same night has a shorter TTL and the same key and topic; a night that is already over gives no options and so no send (`stale`), and a night or offset that is not usable is `invalid_place`. A test walks two days in ten-minute steps for every risk and requires options to exist exactly while `decide` would still send, so the two boundaries cannot drift. These are the values the delivery log records as sent (`pushTtl`, `pushUrgency`, `pushTopic`, data-infra ADR-0003); nothing here sets a header, which is the sender's job. Not in it, on purpose: severe-weather alerts (`weather_core::severe_alert`, below), and every call to the Nyuchi API or a push service. The copy is the existing payload copy and promises no delivery.

**Severe-weather alerts** (`weather_core::severe_alert`, step d, the pure half; no I/O, no clock, no key, so it cannot send anything). **Where they come from:** only an official source that publishes the OASIS Common Alerting Protocol 1.2 (CAP), an alerting authority in the WMO Register of Alerting Authorities (for Zimbabwe, the Meteorological Services Department; the WMO Severe Weather Information Centre's source list shows its feed as `operating`, read 2026-11-04 from `severeweather.wmo.int/json/sources.json`). Never our own thresholds over the blended forecast and never a weather station: a model can say frost is likely, but a warning to leave a flooded valley is the authority's to issue, and the message names the authority. The input is a `CapAlert` (the facts of one `alert/info`, already parsed); reading the XML feed into it is the next step and is not built (a fetch with the `external_fetch` guards, an XML reader, `geocode` tables). `evaluate_severe(alert, lat, lon, now)` returns a `SevereAlert` or the first `Skip` reason, in the gate's order: `invalid`, `not_actual`, `not_public`, `not_an_alert`, `not_weather`, `below_severity`, `not_imminent`, `not_likely`, `no_expiry`, `expired`, `not_yet`, `area_not_matchable`, `outside_area`. **The gate is conservative and every line is one match arm or constant:** `status` Actual (never Test, Exercise, System or Draft), `scope` Public, `msgType` Alert or Update (a Cancel is not pushed), a `category` of Met, `severity` Extreme or Severe, `urgency` Immediate or Expected, `certainty` Observed or Likely, an `expires` not yet passed, an `effective` no more than six hours away, and an area, a polygon or circle, that contains the place. Moderate and Minor warnings, Future and Possible ones are real information but belong in an in-app list, not a push. A test walks every combination of status, scope, msgType, severity, urgency and certainty (9,375) and requires exactly 16 to be pushed. **Fail closed:** an alert whose area is only `geocode` values cannot be matched and is `area_not_matchable` (distinct from `outside_area`, so a coverage gap is visible); an alert with no `expires` has no `TTL` to give and is skipped; an alert with another area given only by geocodes, when the point is outside every shape, is `area_not_matchable` too (the point may be in the area we cannot read), never a quiet `outside_area`; an empty event or authority, or an alert that ends before it starts, is `invalid`; a malformed or oversized shape (more than 256 shapes or 50,000 vertices) is `invalid`, never a quiet `outside_area`; a polygon that winds around a pole is `invalid`, and one that crosses the antimeridian is read the short way. A point on a boundary is inside. `severe_push_options` gives the `TTL` (to `expires`, at most 36 hours), `Urgency: high` for Extreme and for Severe plus Immediate (`bypasses_quiet_hours`, the input to the per-person gate) and `normal` otherwise, and a `Topic` of `sv-` and a 20-character hash of the sender and identifier (it holds no place, cell or person, but the authority publishes the identifier, so a push service that already knows an alert could recognise it and learn that this subscription received it, an area no finer than the authority's). `severe_dedupe_key(cell, alert)` is `{cell}:severe:{token}`, the three-part shape the delivery log requires (the cell's `cell:` prefix is dropped, and a cell that would make a fourth part gives `None`), one key per alert. An `Update` has a new identifier and so is a new alert and is pushed again (a person may see the original and its update); linking by `references` needs the delivery log. `severe_payload` is plain text: the authority's headline (or event), "Issued by {authority}. Open for details.", control characters removed and cut by characters; its `night` field carries a ten-character alert token so two alerts for one place on one day get two notification tags and the second never replaces the first. **Not built:** the per-person gates for this kind (follows the place, quiet hours, daily caps, kind on or off) are `push::decide`'s for frost and are generalised to kinds separately; the feed fetch and XML reader; the `weather.alerts` collection or an inbox entry for the warnings that are not pushed; and the sender.
**Preferences from the Nyuchi API's shape** (`AlertPrefs::from_api` in `weather_core::push`, step d, pure). The API serves a target's preferences as `alert_kinds` (a list of `frost` and `severe`), `quiet_start` and `quiet_end` as `HH:00` strings or both absent, and `place_slugs`; the planner reads `AlertPrefs` (a `frost` flag and two quiet-hour numbers), so the jobs Worker's client needs one place where they meet, and this is it. `frost` in the list turns frost on; `severe`, and any kind a later API adds, change nothing here (the severe kind has its own gate, and an old sender must not guess about a new kind). Quiet hours are two different whole hours exactly as `HH:00` (`00:00` to `23:00`, the API's own `([01][0-9]|2[0-3]):00`), or both absent for none, stored as two equal hours, which `in_quiet_hours` reads as no quiet time at all (not the 22:00 to 06:00 of `AlertPrefs::default`: in the API's model absent is none, its view of a person with no stored preference is "no alerts, no quiet hours"). A half window, two equal hours, a quarter-hour, a single-digit hour, seconds, a space, a newline and full-width digits are `quiet_hours_invalid`, as the API refuses them, so a value the API would not store is never read as something a person asked for; the caller skips that target. The follow list is checked as `AlertPrefs::validate` does. The API's rules above were read from `nyuchi-api` `gateway/lib/web_push.py` at `staging` 3ea461d (`validate_quiet_hours`, `_HOUR`, `ALERT_KINDS`, `preferences_view`); no fixture ties the two repos together, so a change there is not caught here. **Open, not decided (tracked on #289):** the API stores a `quietTimeZone` (the person's), but `push::decide` reads quiet hours in the PLACE's local time, as the first design said. For someone following a place far from where they live, a 02:00-at-the-place push can land in the middle of their day, and a 22:00-at-the-place one can wake them. Reading them in the person's zone when the API gives one, else the place's, would change `DecisionInput` (a second local hour), not this adapter.

**`workers/push` (`mukoko-weather-push`) is the runtime half, and it is dark.** It holds the three things only a Worker can do, each thin, and nothing else:

- `webcrypto::WebCryptoKeyAgreement`: a fresh non-extractable ECDH P-256 pair per message, ECDH against the browser's `p256dh` (WebCrypto's `importKey` refuses a point off the curve, a `DataError`, which is the subscription's fault and nothing else's), the raw public key exported.
- `webcrypto::WebCryptoSigner`: ECDSA P-256 / SHA-256 under the VAPID private key, the raw 64-octet `r || s`. The key is a **value the caller passes in** (`WebCryptoSigner::import(private_b64url, public_b64url)`); it becomes a non-extractable `CryptoKey`, a probe is signed and verified with the public key before the signer exists (a pair that does not belong together is `vapid_key_mismatch`, not a 403 from every push service), and its `Debug` prints nothing. The crate never reads, stores or logs a key and has no secret binding.
- `transport::WorkerPushTransport`: one POST over `fetch`. `redirect: "manual"` (a 3xx is a bare status), one deadline through an `AbortSignal`, only a request that passes `runtime::check_request` (https, a host on `weather_core::push`'s list, exactly the five headers a push carries, one record, a bounded deadline), no cookies, no logging. **The answer's body is never read or kept**: the status and, for a 429 or a 5xx, the `Retry-After` seconds (capped at a day) are all that is taken, and the request is then aborted to release the connection. `Delivery.retry_after_secs` carries the hint; whether a later tick honours it is the evaluator's call. Errors are the stable codes `push_timeout`, `push_network`, `push_refused`.

Its only route is `GET /health`. **It has no scheduled handler, no cron trigger, no send route, no route to alert targets, no queue, no storage, no Secrets Store binding (a binding to a store secret that does not exist fails the deploy, error 10182, and the key pair does not exist yet), no `workers.dev` address and no custom domain.** It is built by CI (the `workers.yml` bundle matrix and its size gate) and is deliberately **not** in `workers-deploy.yml`'s order or choices. `crates/weather-webpush/src/tripwire.rs` reads its source and `wrangler.jsonc` and fails if any of that changes, and if the lockfile gains a RustCrypto curve crate. The PR that turns the sender on deletes the tests it contradicts, in the open.

**What it needs before it can be deployed (all the owner's or later steps'):** the VAPID key pair in the Secrets Store (`MUKOKO_WEATHER_VAPID_PRIVATE_KEY`, the public half as a var) and the contact `mailto:`; the sender key with the `notifications:alert-sender` scope for the Nyuchi API's `/v1/notifications/alerts/*` routes; and the evaluator tick in `mukoko-weather-jobs` that decides, calls this Worker's sender and writes the delivery log. Deploy `push` before `jobs`.

**How the glue was checked.** The WebCrypto calls and the `fetch` transport cannot run in `cargo test`. Their decisions are pure and native-tested (`runtime`), and the two files were compiled to wasm32 and run under Node 22 through wasm-bindgen's JS glue in a scratch harness (not in the repo; `webcrypto.rs` and `transport.rs` unchanged apart from one `use` path, with `fetch` stubbed, so the code exercised is the Rust, but through Node's WebCrypto and not the Workers runtime's): WebCrypto's ECDH output decrypted by an independent implementation of RFC 8291 section 3.4, the ES256 signature verified as a VAPID JWT with `crypto.verify` (`ieee-p1363`), an off-curve point, a zero scalar and a mismatched pair refused with the codes above; and the transport against a stubbed global `fetch` (no network, no push service): a manual-redirect POST with exactly five headers, the answer's body never pulled, `Retry-After` read for 429 and 5xx only, a 3xx not followed, off-list hosts refused before `fetch`, a deadline that aborts through the signal. **That is Node, not `workerd`:** the first run in the Workers runtime is the owner's gate.

The VAPID key pair is an **owner step**: generate it once (a P-256 key; the private half is a Secrets Store secret, the public half is what the Nyuchi API serves from `GET /v1/notifications/push/config` and a browser subscribes against) and set the contact `mailto:`. Never generate or store it from code in this repo. Changing the pair later invalidates every subscription.

## Apple WeatherKit ([#408](https://github.com/mukoko-dev/mukoko-weather/issues/408))

Apple Weather (`apple_weatherkit`) as a forecast model: a pick in My Weather and a series in the model comparison, from the 500,000 WeatherKit calls a month the Apple Developer Program membership includes. **Built:** every host-agnostic rule, in `weather_core::weatherkit` (pure, no I/O, no key, no clock). **Not built, on purpose:** any Worker wiring. The weather backend is moving to Gwaihir, a server of the Nyuchi Servers API (nyuchi/nyuchi-servers-api), so nothing here is served by a Cloudflare Worker and `forecast`, `public-api` and `places` do not know the model (a request for it gets the blend). **Unverified against the live API:** no WeatherKit key was available, so the fixture `tests/fixtures/weatherkit-documented.json` is built from the property tables of Apple's REST documentation and says `provenance: documented`; compare the first real response with it before the model is switched on.

| Module      | Rule                                                                                                                                                                                                                                                                                         | Pinned by                                                                                                                                                       |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `condition` | `conditionCode` to WMO 4677, all 34 documented codes; the nine that describe the air, wind, temperature or a cyclone (haze, smoke, blowing dust, breezy, windy, frigid, hot, tropical storm, hurricane) are `None`, never `0`                                                                | a hand-written table of all 34, agreement with Tomorrow.io's map where the meaning is the same, every emitted code describable by `wmo::description`            |
| `token`     | the ES256 developer token (header `alg`, `kid`, `id`; claims `iss`, `iat`, `exp`, `sub` and nothing else), valid one hour, reused 50 minutes; the signer is injected (`Es256Signer`, raw 64-octet `r \|\| s`) and no signing code or elliptic-curve crate is in the repo (RUSTSEC-2026-0387) | the exact header and claims bytes, validated with a stock JWT library and a real P-256 key in a scratch check                                                   |
| `snapshot`  | the response in OUR form: Open-Meteo names, degrees C, km/h, mm, percent (humidity and cloud cover arrive as 0 to 1), WMO codes, RFC 3339 UTC; implausible numbers dropped, rows capped; sea-level pressure kept as `pressure_msl`, never as the app's `surface_pressure`                    | the fixture, with expected values computed by plain arithmetic outside the Rust                                                                                 |
| `align`     | that form on a place's time axis: period variables (rain, gusts, chance) from the PRECEDING hour, days only when they start at local midnight, the next-hour rate (mm an hour) as 15-minute millimetres, the comparison series, and `compose_raw` for the single-model baseline reader       | the shift, the midnight rule, the nowcast sums, and `blend::blend_payload` reading the composed result                                                          |
| `budget`    | the caps (month 450,000, rolling day 15,000, hour 1,000 for the service and 60 for a client), two classes (a pick gets the full caps, a comparison series half), fail closed, and the two atomic statements as a contract                                                                    | the numbers, the order of checks, an unreadable count refusing, the SQL shape; the statements were also run on SQLite 3.45 (caps, window expiry, change counts) |
| root        | the model id, the request URL (the 0.05 degree cell CENTRE, never the visitor's exact point; one request names all four data sets), the cache key `wk:v1:<cell>` and its TTL (15 minutes, never past Apple's `expireTime`), outcome classification, the attribution                          | the URL, the cache key and TTL, 4xx never counting against the breaker (`breaker::APPLE_WEATHERKIT`, the default: 3 failures in 5 minutes open it for 2)        |

**Retention.** Apple data lives only in the 15-minute cache, in the standard form (the `Snapshot`), and never longer than Apple's own `expireTime` (data with less than 60 seconds left is not stored: `cache_ttl_seconds` is `None`). It is written to no database, the history store, the archive, or `weather.forecastVerification`, and the composed payload is not cached either. In the browser, the service worker holds a `/v1/weather` answer 15 minutes at most, and the 2-hour weather-hint cache and the device store take the server seed (the blend), never an Apple baseline. The Developer Program licence terms on retention could not be read here: the owner must confirm that a 15-minute cache and the blended use are allowed.

**Budget.** One HTTP request is one call however many data sets it names (Apple's developer forums say so; the official pages are silent: check the usage report). Only a cache miss spends. The two classes (a pick, a comparison series) do not authenticate anything: `?model=` and `models=` are both anonymous query parameters, so a deliberate abuser can spend a pick's full caps; the per-client hour, the service hour, the rolling day and the month bound the damage, and the origin should rate-limit by client before it reaches the budget. The rolling windows are counted from `rate_events`, whose rows are pruned after 24 hours, so a calendar month cannot be counted there: the month is a counter row with a guarded upsert. The rolling statement runs first, the month counter second, and a call goes out only if both write; any error is a refusal and the answer is the blend, labelled (`baseline.reason`: `not_configured`, `budget_exhausted`, `budget_unavailable`, `circuit_open`, `upstream_error`, `auth_failed`, `no_data`).

**Clock changes and odd zones.** The local-time axis carries one UTC offset, so a clock change inside the 7 days would put every later slot an hour off. The module detects it from Apple's own day starts (`align::clock_change_from`) and leaves the day of the change and everything after to the filler: Apple's hours and sun times are left out, never read misaligned, so the weeks around a change are mostly `best_match`. A caller that asks Open-Meteo for `timeformat=unixtime` passes exact instants to `align::hourly` and has no such limit. For a zone that is not a whole hour from UTC (India, Nepal, Newfoundland) a slot takes Apple's nearest row within 30 minutes, since whether Apple starts its hours on the local or the UTC hour is not documented.

**Not done.** Weather alerts (Apple publishes them for select regions, Africa unlikely: they need `countryCode`, must link Apple's alert page and name the source agency, and may never be edited). Apple's official mark as an image (the credit is the trademark text until `markAssetUrl` is wired; the feature flag stays off until then, and the CSP `img-src` needs Apple's host).

The Apple account steps are an **owner step** (CONTRIBUTING.md, "Apple WeatherKit"); never create the key or the secrets from code in this repo.

## MongoDB from a Worker

Workers cannot use the `mongodb` crate, and the Atlas Data API was shut down on 30 September 2025, so `crates/weather-mongo` speaks the wire protocol itself over `worker::Socket` (outbound TLS): `OP_MSG`, SCRAM-SHA-256 and a small BSON codec. The logic is tested natively (the BSON specification examples, the RFC 7677 SCRAM vector, and a scripted server that runs the whole login), but it has not yet been run against a live cluster: use the probe below as the first check.

Owner steps:

1. **Atlas network access.** A Worker has no fixed address, so the Atlas project's IP access list must allow `0.0.0.0/0` (Atlas, Network Access). Protect the cluster with a dedicated database user instead: a **read-only** user (`read` on `weather` and `places`) named for this backend, with a long generated ASCII password (SCRAM-SHA-256; a non-ASCII password is refused).
2. **The connection string, as a seed list.** A Worker cannot resolve `mongodb+srv://`. In Atlas, "Connect" then "Drivers", choose an older driver version to show the `mongodb://` form that lists every shard host, and keep `authSource=admin`:
   `mongodb://USER:PASSWORD@ac-xxxx-shard-00-00.xxxx.mongodb.net:27017,ac-xxxx-shard-00-01.xxxx.mongodb.net:27017,ac-xxxx-shard-00-02.xxxx.mongodb.net:27017/weather?replicaSet=atlas-xxxx-shard-0&authSource=admin&tls=true`
3. **The secret.** Create it in the Secrets Store as `MUKOKO_WEATHER_MONGODB_URI` (scope `workers`), then add the `secrets_store_secrets` binding to each Worker that reads MongoDB and list that Worker in `weather_core::secrets::ALL`. Until then, set the plain secret on that Worker: `npx wrangler secret put MONGODB_URI -c <worker>/wrangler.jsonc`. (Do not add the binding before the store secret exists: Cloudflare refuses the deploy, error 10182.)
4. **Check it.** `GET` the forecast Worker's `/health?probe=mongo` (through a service binding, or `wrangler dev`) answers `mongo_probe: {"ok": true}` once the network path, the string and the login all work; on failure it names the problem (never the string).

## The MongoDB bridge

Devices and community reports are stored in MongoDB, not D1. `weather-mongo` is read-only, so writes go through `mongo-bridge` (`mukoko-weather-mongo-bridge`, TypeScript): one Durable Object holds one `MongoClient` from the official `mongodb` driver (`nodejs_compat`), so the connection is set up once instead of about 300 ms per request. A `MongoClient`, `Db` or `Collection` cannot cross RPC, so all database logic runs inside the object and callers speak narrow JSON over HTTP. It has no route and no workers.dev address; only a Worker with a `MONGO_BRIDGE` service binding (`places`) can call it.

| Route (bridge)                                          | Collection                                                                                                                                   |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /devices`, `GET`/`PATCH /devices/{id}`            | `device.device_profiles` (`{deviceId, preferences, createdAt, updatedAt}`)                                                                   |
| `POST /reports`, `GET /reports`, `POST /reports/upvote` | `weather.weather_reports` (the shape the Python backend wrote)                                                                               |
| `GET /history`, `POST /history/days`                    | `weather.weather_history` (`{locationSlug, date, source, current, daily, insights?, recordedAt}`; read any source, INSERT archive days only) |
| `GET /places?slug=`                                     | `places.placesGeo`, READ ONLY: a community place by `sourceProvenance.mukokoSlug` (404 none, 503 not readable)                               |

The document shapes are the existing ones: nothing is migrated. Every route validates its input with the rules of `weather_core::community` (the Rust Worker checks first, the bridge again), builds its own query from the validated fields (no filter, update or projection from the caller), bounds every list (at most 20), and applies an upvote in one atomic update (`$addToSet` plus `$inc`, only when the voter is new). Indexes are never created from code. The history routes are bounded the same way: a read is at most 3 keys over 3660 days; a write is at most 800 archive days (the body cap for that route is 1 MiB, the others 16 KiB) whose `source` must be `nasa-power` or `open-meteo-archive` (a `recorded` day can never be written through the bridge), whose fields are an allowlist of typed numbers and `YYYY-MM-DDTHH:MM` strings, and whose dates are past and at least 1940; the document is built by the bridge, inserted `$setOnInsert` with upsert (unordered, a duplicate-key race is not an error), so a stored day is never overwritten. Per-client limits (20 fresh devices an hour; the history budgets) stay in the calling Worker, in D1 `rate_events`.

Owner steps:

1. **Atlas user.** Create a read-write database user for the bridge (`readWrite` on `device` and `weather`, plus `read` on the collection `places.placesGeo`, which the history route reads to find a place's platform slug and `GET /places` reads to find a community place by its app slug; nothing else), with a long generated ASCII password. Without the `places` read the bridge still works, except that `GET /places` answers `503` (so a report for a community place, and `/v1/locations?slug=` for a slug no other source knows, answer `503` rather than `404`) and the alias lookup fails closed (no alias days are merged, one warning with the error name, retried after 5 minutes). The Atlas IP access list already allows Workers (see "MongoDB from a Worker").
2. **The secret.** Put the seed-list connection string (the same form as in "MongoDB from a Worker", with this user, `authSource=admin`) in the Secrets Store as `MUKOKO_MONGODB_RW_URI` (scope `workers`) BEFORE the first deploy: a binding to a store secret that does not exist fails the deploy. The bridge reads the store binding, and falls back to a plain Worker secret `MONGODB_RW_URI` (`npx wrangler secret put MONGODB_RW_URI -c mongo-bridge/wrangler.jsonc`) while the store entry is missing.
3. **Indexes** (Mongo shell; not created from code): `weather.weather_reports` TTL index on `expiresAt` with `expireAfterSeconds: 0` and `{locationSlug: 1, reportedAt: -1}`; `device.device_profiles` unique `deviceId`; `weather.weather_history` already has its unique `{locationSlug: 1, date: -1}` index (db-init created it), which is what makes the history insert-only upsert race-safe. Without the unique indexes two simultaneous creates of one new device id (or of one history day) could both insert. The bridge's read-write user needs `readWrite` on `weather` already (reports).
4. **Deploy order.** `mongo-bridge` (`cd mongo-bridge && npm ci && npx wrangler deploy`), then `places`, then `ai` (it binds `places` for the history analysis), then `public-api` if it changed. Check it: `GET /health?probe=mongo` on the bridge (through the binding or `wrangler dev`) answers `mongo_probe: {"ok": true}` once the network path, the string and the login work; on failure it says `not_configured` or `unreachable`, never the string.

## Rules

- **Cloudflare only.** Work that does not fit a Worker goes to Queues, Cron Triggers, Durable Objects, Workflows or Containers, never another host.
- **MongoDB, read-only, through `weather-mongo`.** The Workers keep weather data in their own D1, KV and R2, and may read the shared MongoDB (`places`, `weather` reference data) with `weather_edge::mongo(env)`: `find`, `find_one` and `aggregate` only (no `$out` or `$merge`), read preference secondary-preferred, a server-side time limit and a cap on the documents returned. It needs the connection-string secret and the owner steps below. Canonical records are still written only through the Nyuchi API (#150).
- **Keep each Worker small.** Budget its CPU, memory, bundle size and subrequests. Split a Worker, or fan out over a Queue, rather than grow one.
- **Observability.** Traces and invocation logs are on, with query strings redacted. The code never logs payloads, coordinates or keys.
